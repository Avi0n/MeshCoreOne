# WP-501 source, case-family and consumer acceptance

The full accounting is generated by `android/parity-tests/audit.py`, from the
unchanged manifest and the **actual parsed pinned originals**. It contains every
one of the 1,866 source/resource/license/reference paths and 5,133 original
path/case/parameter-family identities. The original detailed assertion sites,
helper invocations, conditional traits and complete parameter expressions/rows
remain in `docs/android/evidence/WP-004/inventory-details.json`; both the entire
detail structure and each referenced declaration are digest-bound.

Three case IDs occur in more than one original path. A case name alone is not
an identity. The key is **source path + case ID + parameter family**.
Every excluded family stays visible with its actual current manifest exclusion,
never a passing result. This includes 66 historical declarations in nine
removed-translation test/helper paths. Other billing/Apple-only exclusions
remain separately identified. Original text, localization and unlocked themes
remain in scope.

## Policy and evidence semantics

`coverage-policy.json` implements the charter's existing strict requirements,
not a new numerical coverage threshold or self-approved exception:

- All inputs and all original families must be accounted for.
- A header, case-marker annotation, filename, matching method name or passing
  aggregate is **not** proof of equivalent assertions or consumer behavior.
- Historical mappings and pass claims are candidates for inspection, not
  exact-head execution evidence.
- Mandatory skipped/zero/malformed/failed reports fail; no new exclusions,
  golden updates, translation re-admission or reduced thresholds are permitted.
- Independent behavior/family review and independent in-scope oracles remain
  required. Candidate workers cannot approve themselves.

`accounting.json` deliberately reports **BLOCKED behavioral acceptance**.
`--check` succeeds only for reproducible, complete accounting and explicitly
prints that separate blocked acceptance. `--require-acceptance --pr <number>
--base-sha <sha> --head-sha <sha>` reads the existing authenticated GitHub gate
authority. Only a current authoritative external review with all acceptance IDs,
no blocking findings and actual successful execution can resolve acceptance.
Candidate JSON, stale revisions, local PASS and PR prose cannot approve it.
No command publishes a check, configures the trusted publisher or merges.

Candidate mappings are found from pinned `PortedFrom` headers, original-case
markers and explicit predecessor `source-cases.json` proposals. Their presence
does not establish equivalence. Missing recognized mappings are **review
worklist entries, not proven missing implementations**: dynamic test factories,
many-to-many implementations and other predecessor evidence must be inspected
before filing a product defect. Unresolved markers (including production
scenario labels that are not registered original tests) stay visible rather
than being guessed into the original inventory.

## Executable gap fill

The app's existing test-only source set includes `android/parity-tests/src/test`.
There is no new module or production/test dependency and no acceptance fixture
is compiled into the APK.

`MessageBackupAcceptanceTest` executes the real codec, real in-memory Room
store and production process chat consumer. Six separately discovered text
families (CJK, mixed RTL, ZWJ emoji, decomposed accent, composed accent,
whitespace/quote/URL) assert:

- UTF-8 original text, UInt32 maximum timestamp and fractional Unix dates
  survive export/decode/restore;
- two intentional identical outgoing sends keep both UUIDs and reply identity,
  without content-based collapse;
- reimport inserts no duplicate messages;
- both restored messages reach the mounted native timeline without creating
  a connection or fake radio.

Additional tests exercise invalid manifest rejection before transaction,
successful recovery in the same process store, and cancellation identity/input
closure. An independent consumer assertion restores the **actual pinned
Swift-produced** 1,835-byte backup (checked against its measured SHA-256),
verifies original UTF-8/binary/UInt32/fractional Unix fields, and observes the
message in the offline native timeline. Expected bytes are not generated by
candidate Kotlin. These extend pinned backup cases into an offline consumer
acceptance family; they do not claim new Swift execution or physical radio
delivery. A source-literal redaction assertion independently checks all safe
radio defaults, including SF10 and CR5, without calling candidate redaction
code to produce its expectations. A device update regression preserves the
original pre-repeat SF8 and all radio fields without mutating the input.

The mounted `AppChatContent` caller-timeout assertion established a product
defect: the app catches the caller's one-second timeout as its own thirty-second
failure. The complete [issue-ready report](../evidence/WP-501/inline-caller-timeout-defect.md)
was immediately [posted for coordinator repair](https://github.com/cbattlegear/MeshCoreOne-Android/pull/165#issuecomment-6111573158).
The coordinator filed [#166](https://github.com/cbattlegear/MeshCoreOne-Android/issues/166)
and is repairing it. The assertion remains failing on the current product bytes;
the worker does not edit that product path.

Two further gap assertions restore the original real-store discovered-node
deletion through the actual app/Room adapter and exact source contact-URI
name/key/type/whitespace assertions through the real encoder/parser.
The discovery case also checks another radio's same-key record and a subsequent
reload. These new cases await native execution; the predecessor's fake-store
delete and adapted contact name/key are not promoted as their proof.

`FreshStoreBackupAcceptanceTest` adds three actual distinct-database routes:
export/decode/import of the original Alice/General/Hello graph with reaction
parent identity, type4/CHAT fallback, targeted ordered regions, exact heard600
and avatar22 fields; the original channel-message/repeat42 cascade; and
the source32-byte secret with inherit/US flood scope.
Source and destination stay simultaneously open, source rows are never cleared,
and restored Hello reaches the offline native timeline. These fill the
clear-source adaptation's missing evidence; native execution is still pending.

The current app JUnit collector requires every exact WP-501 class/method identity,
not merely seventeen arbitrary passing tests. All existing module/primary suite
checks remain. The Python audit regressions exercise duplicate/path-qualified
families, full parameter provenance, drift, exclusions, no header/historical-pass
promotion, and missing/zero/failed/error/skipped/malformed/duplicate JUnit cases.

## Source-backed semantic comparisons

`semantic.py` reads every actual pinned original declaration and native
method/named-lambda body. The 58 owner worklists in `groups/` preserve original
assertions, parameter expressions, actions, helper references, compile conditions
and actual native assertion/registration bodies. This lexical extractor is not
a compiler, a behavioral oracle or automatic equivalence.

`review-proposals.json` contains **242 actually inspected families in 29 groups**:
crypto22, model41, backup41, coordinates/mentions/link-tokenization75 and
contact/share/QR/discovery20, localization2 and backup-integration41.
Each proposal explains exact inputs/assertions, helper and consumer behavior,
native adaptations and unresolved scope. `review-bindings.json` binds that prose,
actual source/native/helper bytes and precise JUnit class/display identities.
Annotated JUnit4 renames, dynamic factory identities and many-to-many
feature/app targets are resolved explicitly. The combined app contact-URI case
serves two original declarations but is not counted as two native executions.
Ambiguous bodies, missing assertions, incomplete declared group coverage or stale
generated bytes fail closed. An explicitly partial source-file group retains the
file's total family count and selected group count; unknown, duplicate or empty
subsets fail and the same original cannot inflate comparisons across groups.
The remaining86 backup-integration declarations are still uninspected work,
not exclusions or passing families. [Resource review](resource-review.md) binds
actual source format/plural/locale/helper comparisons and the converter outcome.

`semantic.py --check --verify-execution` additionally requires those exact cases
in the current candidate's actual reports; historical pass totals are not promoted.
The existing full scaffold stage invokes this after collecting primary/module
JUnit. The 242 proposals are a bounded reviewable implementation increment,
**not completion of the full original/consumer/resource audit**. Other families
and source/resource contracts remain worker audit work, not an unavailable
hardware gate or an independent-review-only preparation stop.
