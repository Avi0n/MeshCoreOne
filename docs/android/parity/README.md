# WP-501 source, case-family and consumer acceptance

The full accounting is generated by `android/parity-tests/audit.py`, from the
unchanged manifest and the **actual parsed pinned originals**. It contains every
one of the 1,866 source/resource/license/reference paths and 5,133 original
path/case/parameter-family identities. The original detailed assertion sites,
helper invocations, conditional traits and complete parameter expressions/rows
remain in `docs/android/evidence/WP-004/inventory-details.json`; both the entire
detail structure and each referenced declaration are digest-bound.

Three case IDs occur in more than one original path. A case name alone is not
an identity. The key is **source path + case ID + parameter family**.
Every excluded family stays visible with its actual current manifest exclusion,
never a passing result. This includes 66 historical declarations in nine
removed-translation test/helper paths. Other billing/Apple-only exclusions
remain separately identified. Original text, localization and unlocked themes
remain in scope.

## Policy and evidence semantics

`coverage-policy.json` implements the charter's existing strict requirements,
not a new numerical coverage threshold or self-approved exception:

- All inputs and all original families must be accounted for.
- A header, case-marker annotation, filename, matching method name or passing
  aggregate is **not** proof of equivalent assertions or consumer behavior.
- Historical mappings and pass claims are candidates for inspection, not
  exact-head execution evidence.
- Mandatory skipped/zero/malformed/failed reports fail; no new exclusions,
  golden updates, translation re-admission or reduced thresholds are permitted.
- Independent behavior/family review and independent in-scope oracles remain
  required. Candidate workers cannot approve themselves.

`accounting.json` deliberately reports **BLOCKED behavioral acceptance**.
`--check` succeeds only for reproducible, complete accounting and explicitly
prints that separate blocked acceptance. `--require-acceptance --pr <number>
--base-sha <sha> --head-sha <sha>` reads the existing authenticated GitHub gate
authority. Only a current authoritative external review with all acceptance IDs,
no blocking findings and actual successful execution can resolve acceptance.
Candidate JSON, stale revisions, local PASS and PR prose cannot approve it.
No command publishes a check, configures the trusted publisher or merges.

Candidate mappings are found from pinned `PortedFrom` headers, original-case
markers and explicit predecessor `source-cases.json` proposals. Their presence
does not establish equivalence. Missing recognized mappings are **review
worklist entries, not proven missing implementations**: dynamic test factories,
many-to-many implementations and other predecessor evidence must be inspected
before filing a product defect. Unresolved markers (including production
scenario labels that are not registered original tests) stay visible rather
than being guessed into the original inventory.
