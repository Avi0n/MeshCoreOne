## R118 CM-05 / CM-08 issue #388

The maintainer explicitly selected retaining recoverable Android failure behavior
in session `0872d489-506f-4cd4-984f-3715cd4a8a8c`: per-entry persistence
diagnostics, unresolved ACK retention and failed-hydration retry without duplicate
envelopes. This is a bounded native adaptation, not literal equivalence to Swift's
pre-read hydration latch or `failAllPendingMessages` clearing the entire tracking
map before its first throwing store write.

The explicit fail-all operation now processes independently writable entries
after a typed persistence failure, reports and retains each failure, and throws
the first persistence error (with other distinct errors suppressed) after the
sweep. Only committed entries retire tracking and emit failure notifications.
Retries, committed ACK delivery and successful expiry clear resolved fail-all
diagnostics, so recovered tracking cannot leave a false incomplete-teardown report.
The persistence write and its failure/recovery bookkeeping share the per-message
mutation lock, preventing an overlapping retry from resolving an entry before a
late failure diagnostic is recorded.
Cancellation and obsolete ownership still
terminate the operation immediately; they are not storage failures or successful
teardown. Routine disconnect behavior is unchanged.

The three original negative windows are retained as 200/300/1000 milliseconds on
the same injected scheduler used by the real queue, message service and protocol
session. The 300ms case restores the original two-retry/10ms-base pool backoff and
collects status events throughout the interval. Packet counts and persisted
attempt/message outcomes discriminate a real parked send from an immediate
snapshot or an unexercised error path. No production deadline is shortened.

All seven assigned original families remain enabled. Eleven supplemental cases
cover per-entry expiry/fail-all errors and retry, retained teardown causes,
cancellation, successor ownership, raw ACK delivery reconciliation and coalesced
hydration, including overlapping fail-all failure/retry and failure followed by
ACK or expiry recovery.
These use the actual services/session with RecordingStore, not Room.
Existing actual Room hydration, expiry/recovery, fail-all/queue and terminal-row
tests remain unchanged and must run as downstream consumers. New Room-support
edits were rejected by trusted admission and are tracked with supervised software
verification in #452; no capability, policy, source pin or gate is changed here.
See [the concern mapping](../evidence/WP-208/r118-queue-ack-contracts.md).

## Bounded queue-query progress repair (WP-501 issue #261)

The frozen queue keeps a per-envelope consecutive query-failure counter, with
disambiguation after three send attempts and a default cap of sixteen actual
query throws. Android's per-connection graph replacement discards that counter
after a real query timeout fences the session. Retrying on a fenced session is
not another query failure and is not evidence that the channel is absent.

`ChatSendQueueProgress` is an Android process-lifetime adaptation, explicitly
injected into replacement queues. It retains only counters, partitioned by
radio/message identity and bound to the persisted pending-row UUID. All drains,
subscriptions, ACK waiters, transports and services remain connection-owned.
Attaching a newer generation fences all older progress leases. Retiring a lease
does not erase pending counters; successful hydration prunes deleted/replaced
rows for that radio. Genuine query success resets the counter, including a real
null result; successful send/terminal deletion also clears it. Terminal storage
failure retains progress so reconnect does not restore a full retry budget.
Cancellation and stale ownership checks are not query failures.

The optional constructor argument preserves existing callers' historical local
lifetime. It is NOT the App fix. WP-303 must retain a single owner in AppContainer,
pass it through SessionEnvironment (including withLifecycle reconstruction), and
inject it into every ChatSendQueueService. No App, database/schema, runtime,
protocol fence or shared WP-501 fixture is changed here. WP-207 separately owns
physical recovery after CorrelationUncertain. Whole-bug acceptance requires both
actual consumers and fresh WP-501 App-edge execution.
In particular, the protocol emits uncertainty before the caller necessarily
observes its query failure; Default-dispatched runtime recovery may retire the
queue first. The queue's concrete `suspend fun awaitChannelQueryAccounting()`
now seals further send/query admissions and observes its actual
generation/message/pending-row-bound query through
genuine outcome accounting and pending-status park or terminal persistence.
WP-207 must await it, through WP-303's actual graph delegation, before token
withdrawal, scope cancellation, lease retirement and physical teardown.
Manual stop/replacement cancels the observation; observer cancellation does
not cancel the query or reopen admission. Both drains stop after the admitted
envelope, not by cancelling it. Durable enqueues remain pending for the next
graph. The barrier is not a drain join, grace delay, failure
counter or default-success graph hook. Source ChannelService retry timing and
the correlation fence are unchanged. Nine new deterministic cases include
early recovery inside the actual ChannelService retry window and blocked
terminal deletion while the token remains current, exact B attempt-count
preservation before recovery resumes, idle preparation followed by competing
direct/channel enqueues, and preparation during suspended preflight.
The real App edge must still prove that the actual consumers adopt this
ordering. A correlation diagnostic/cancellation is not substituted for a query
failure, and lower-level tests do not establish complete App acceptance.

Sixteen supplemental deterministic cases exercise the concrete MessageService,
MeshCoreSession and raw firmware transport with RecordingStore. They include the
default sixteen genuine timeout threshold across sixteen session replacements,
the unchanged 1,999/2,000ms query observation window, same-channel envelope B
survival after A fails, reset/cleanup, pending-row identity, radio isolation,
cancellation, storage failure and non-cooperative late query completions.
RecordingStore is not Room/device/process-death compatibility evidence. Tests
are authored, not passing evidence until actual runner discovery/execution.
See `docs/android/evidence/WP-208/queue-recovery-accounting.md` for exact outcomes
and the truthful advisory-reservation/local-readiness limitations.

WP-303's intervening no-new-API decision was superseded by the coordinator's
independent WP-501 source review: typed Failure logs occur before persistence,
and retirement can follow failed/cancelled accounting. Local removal0aa was
never published. This successor retains the already published7c1049828
ChannelQueryAccountingEvent/onQueryAccounting API as passive post-persistence
receipts carrying actual token, message/pending identity, dynamic failure count/
cap and exact typed query cause. PARKED follows committed PENDING remapping;
TERMINAL_DELETED follows committed FAILED plus pending deletion/cleanup.
The existing status-write Boolean additionally filters missing/delivered-row
no-ops without changing persistence or send policy. Both callbacks precede
the unchanged barrier release: they are not already-completed-barrier events.
No runtime hook/barrier restructure, await/test gate or synthetic outcome is added.

The original nine accounting and sixteen progress cases are preserved, with
eight more accounting cases and stronger persistence/identity/cancellation
assertions authored but not executed locally. The App witness must capture the
live token on A1/PARKED, A2/TERMINAL_DELETED and B1/PARKED receipt arrival,
verify actual Room outcomes and finished retirement, and reject both accounting
cancellation/failure runtime fallbacks, remap/terminalPersistence and teardown
issues before B's literal-three-second survival can count. The coordinator
holds all pushes pending review and WP-003's safe publication route; blocked
installed-runtime/old66bd guards remain untouched. Neither lower7c nor this
unpublished successor is claimed validated; stack282 order [278,281] is retained.
