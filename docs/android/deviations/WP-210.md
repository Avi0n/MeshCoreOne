# WP-210 native remote node, node config and admin adaptations

Reference: `db14559b39d32322b06477c6ae676112f583db50`.
Owner: `services-porter`. **External contribution:** this was prepared outside the
dispatch controller, with no lease, session or receipt. These are proposed
adaptations for coordinator review. All code is pure JVM in
`core/services/.../services/remote/`. `TelemetryModes` reuses its existing
`core:model` implementation.

## R118 partial-import and lifecycle decisions

For issue #387, the maintainer selected a partial-import warning when a contact
was added to the radio but cancellation or local persistence failure interrupts
its local save. Android now publishes contact progress immediately after the
device confirms the add, propagates caller cancellation, and stops on a typed
local-save failure. The UI's existing partial-failure path can then report
that a device change may have landed. Retrying reads device contacts before
planning and saves the actual unchanged device record locally without repeating
the radio write. The local-only save is not reported as device-write progress;
its failure still stops the import. This is not a claim that a radio write can
be rolled back.

For the same retry, the maintainer chose to treat a contact whose only
difference is `lastModified` as unchanged: the radio's actual timestamp is
saved locally and no radio write is repeated. Swift re-emits such a contact,
so Android also skips an intentional timestamp-only import. The two affected
original planner cases retain their names for traceability and assert this
approved adaptation instead of source behavior.

The local-save failure has Android-only recovery copy in the twelve supported
settings resource locales. The app adapter recognizes the concrete service
failure and supplies that classification to the settings resource mapper,
without introducing a feature-to-services dependency or changing the frozen
neutral fault contract. The message states that the radio accepted the contact,
that local saving failed, and that the import can be retried. The existing
partial-progress warning remains separate. These strings are not Swift source
translations or evidence of complete WP-210 acceptance.

This intentionally differs from the Swift log-and-continue treatment of local
save errors. A store-internal cancellation while the caller remains active is
reported as a local-save failure; actual caller cancellation still propagates.
An in-flight radio command whose result was never observed remains uncertain,
not a confirmed add.

The maintainer selected deterministic job and subscription teardown as the
Android lifecycle criterion instead of an immediate GC deadline. The original
weak-reference regression is retained; the additional teardown test does not
prove that a JVM object is collected at a particular time.

## A-01: shared shape

Confined state behind a lock and an injected `CoroutineScope` replace actors.
Nothing suspends while holding a lock. Clocks, wall time and sleeps are injected,
so every test runs on virtual time. `deinit` becomes `close()`, which also fails
parked logins, in-flight CLI calls and queued slot waiters with
`RemoteNodeError.Cancelled` instead of leaving them parked.

Cancellation is never swallowed. Wherever Swift's `try?` or a catch-all would
absorb it, Kotlin rethrows. One exception follows Swift: a `CancellationException`
a store raises itself, such as an internal timeout, while the caller is still
active, is an ordinary failure. It is logged and falls back exactly where Swift
logs every store error.

Sessions, messages and events are keyed by `EntityKey` (radio plus id), not
`UUID`. The Android store partitions rows by radio. Because of that,
`handleBLEDisconnection` and the admin services' `getConnectedSession` take a
`radioId`, since `RoomPersisting.fetchConnectedRemoteNodeSessions` is per radio.
Swift's query was global, so stale connected rows on another radio are not cleared
by one radio's link loss.

Collaborators owned by other work packages sit behind narrow interfaces, each
documented with the class expected to implement it:

| Interface | Swift equivalent | Expected implementer |
| --- | --- | --- |
| `RemoteNodeSessionPort`, `BinaryProtocolSessionPort` | `MeshCoreSession` | adapters included for a real session |
| `RemoteNodeStore`, `RemoteAdminStore` | `PersistenceStore` slices | adapters over `RoomPersisting` and `ContactPersisting` included |
| `RemoteNodePasswordStore` | keychain | WP-204 |
| `RemoteCommandAuditLog` | `CommandAuditLogger` | WP-212 |
| `NodeConfigSettingsPort` | `SettingsService` | WP-211 |
| `NodeConfigChannelWriter` | `ChannelService` | WP-209 |
| `NodeConfigContactsChangedNotifier` | `SyncCoordinator` | WP-214 |
| `RoomMessageRetryConfig` | `MessageServiceConfig` | WP-208 (Swift defaults kept) |

Swift's audit logger, `onTimeoutKnown` callback and event handlers cannot throw.
Their Kotlin counterparts can, so a failure in any of them is logged and contained.
It never aborts a login or ends event monitoring, and never reaches the
uncaught-exception handler. `NonThrowingAuditLog` wraps every audit hook, and a
reflection test fails if a hook is added without forwarding.

Event streams use a small lock-confined broadcaster that registers at subscribe
time, like Swift's `EventBroadcaster`. Swift unregisters a stream when it is
deallocated. Kotlin can only unregister when collection ends, `finishEvents()`
runs or the service closes. **A caller that opens `events()` must collect it.**

Regexes never rely on `UNICODE_CHARACTER_CLASS` or on the meaning of `\d`/`\s`.
Android's `java.util.regex` is ICU-backed, and the flag and those shorthands are
not portable between it and the JVM. Swift's Unicode `\d` and `\s` are spelled as
`\p{Nd}` and an enumerated White_Space set; a test proves they match the JVM's
flagged classes for every code point. ASCII-only number syntax uses `[0-9]`.

Logging uses `java.util.logging`, matching the package. `PersistentLogger`
belongs to WP-212.

## A-02: RemoteNodeService

The login, CLI, keep-alive, path recovery, reconnection and telemetry policies
match the source, including timeouts, retransmit spacing, heal-and-retry on
`NOT_FOUND`, permission mapping and event order. The differences are:

- **Cancelled callers:** a cancelled login or CLI caller throws
  `CancellationException`. Swift hands it `.cancelled` or `CancellationError`.
- **Ownership:** cancelling removes only the caller's own pending login. Overlapping
  logins swap in one locked step. A CLI waiter cancelled while it is being handed
  the slot passes the slot on. The re-auth guard in `handleBLEReconnection` is
  claimed atomically. Each of these closes a window Swift's actor reentrancy left
  open.
- **CLI attempt ids:** each CLI exchange attempt gets its own request id. The
  path-recovery retry can't be matched by the first attempt's late completion
  handler.
- **Monitor restart:** `startEventMonitoring` cancels the previous monitor before
  subscribing, as Swift does.
- **Types:** Swift `Int` maps to `Long` in `CLIResponse`.
  `KeepAliveRetryPolicy` returns the updated failure count instead of mutating an
  `inout`. `NodeSettingsResponseParser` returns small data classes instead of
  tuples. Wire timestamps use the injected clock's wall time.
- **Text:** `RemoteSwiftText` reproduces Swift's `Int()`, `Double()`, trimming and
  Character-count rules. Fallback error text uses Kotlin's `MeshCoreException`
  message.
- **Already ported:** `TelemetryResponse.dataPoints` is already a member of the
  protocol type with the same decoding, so no extension was added.

## A-03: node config and snapshots

Export matches iOS's `[.prettyPrinted, .sortedKeys]` output byte for byte.
`core:services` has no JSON library, so `NodeConfigJsonSyntax` is a hand-written
reader and writer. Its behavior was checked against real Foundation output with
the oracle in `docs/android/evidence/WP-210/foundation-oracle/`. That run showed
three ways Foundation's decoder departs from strict RFC 8259. Kotlin matches all
three.

- **Duplicate keys:** a duplicated key resolves to its first occurrence, at every
  level and including `null`.
- **Trailing commas:** one trailing comma before `}` or `]` is accepted. `{,}`
  and `[,]` are not.
- **Lazy validation:** string escapes, control characters and number grammar are
  validated only when a field is decoded. An unknown key or a shadowed duplicate
  never fails an import. Structure, literals and the leading character of a
  number are checked eagerly.

Planner name comparisons follow Swift `String` semantics:

- **Equality:** canonical equivalence, decided by NFC normalization. This covers
  hashtag slot folding, the no-op channel skip, the overwrite flag, the contact
  skip and the node-name gate.
- **Hashtag prefix:** `hasPrefix("#")` compares whole Characters, so `#` followed
  by a combining mark is not a hashtag.

`NodeConfigSwiftText` reproduces `Double.description` and Swift's `Double()`
parsing, so coordinates round-trip as on iOS. Where Swift would trap on an
out-of-range number, Kotlin saturates; device data can't reach those values. The
settings port detects firmware's "private key export disabled" error anywhere in
the cause chain, so **WP-211 must pass that error through** rather than replace it.

## A-04: admin services and room server

`RepeaterAdminService`, `RoomAdminService`, `RoomServerService` and
`BinaryProtocolService` follow the source's request building, paging, polling
limits, retry and flood-fallback schedule, dedup and ACK handling. The differences
are:

- **Cancelled sends:** a cancelled room-message send is saved and broadcast as
  failed before the cancellation is rethrown. Swift's send task is never
  cancelled, so without this the message would stay pending forever.
  `postMessage` therefore starts the send `ATOMIC` from a `finally`. A caller
  cancelled during the audit call, or a scope cancelled before the send runs,
  still resolves the saved pending row. Once the radio has transmitted, the
  delivered or sent update runs non-cancellably.
- **Monitoring:** a throwing push handler in `BinaryProtocolService` is logged
  and contained, and a restart cancels the old monitor first, as in A-01.
- **Eager subscription:** `BinaryProtocolService` subscribes to events
  immediately. Swift subscribes inside a new task and can miss pushes that arrive
  before it first runs.
- **Constructor:** `BinaryProtocolService` drops the persistence store, which
  Swift takes but never reads.
- **Shared state:** the default audit logger is shared with `RemoteNodeService`.
  The event broadcaster is a generic `RemoteEventBroadcaster<T>`, since
  `core:runtime`'s `EventBroadcaster` can't be a dependency here.
- **Saturation:** `UInt32(seconds)` saturates through `epochSeconds32` instead of
  trapping.

## A-05: neutral fault carrier (`external-WP210-neutral-fault-amendment`)

The maintainer approved this seam on PR #50. This PR is the only writer of
`android/core/contracts/src/main/kotlin/com/meshcoreone/android/core/contracts/domain/errors/RemoteRoomNodeConfigFaults.kt`
(package `com.meshcoreone.android.core.contracts.domain.errors`). The file is pure
JVM, and its `// PortedFrom:` headers name the four Swift error sources. It adds
four sealed families under PR #49's `SourceServiceFault` root, one case per Swift
case:

- `RemoteNodeFault` (14), `RoomServerFault` (6), `BinaryProtocolFault` (5) and `NodeConfigServiceFault` (9).
- `NodeConfigRadioField` and `NodeConfigCoordinateField`, neutral typed mirrors of
  the `core:services` `RadioField` (5 cases) and `CoordinateField` (4 cases). They
  have the same cases, and the contact name is carried as the same `String`
  instance. The projection is an exhaustive `when` over the typed producer value.
  It never goes through names or strings.

Cases without a payload are `data object`s. Cases with a payload are `data class`es
with `val` fields that carry the raw values exactly:

- the Remote login/send `reason` and the Room send `reason`, as the same `String` instance;
- for every `SessionError`, the producer's identical `MeshCoreException`, including its own cause chain;
- the NodeConfig `index`, `hexLength`, `name`, `UByte` `mode`, `needed`, `available` and typed fields.

`RemoteNodeFault.isRetryable` carries Swift's `RemoteNodeError.isRetryable`, which is
true exactly for `timeout`, `notConnected` and `floodRouted`. It is an exhaustive
`when`, so a new case has to choose a value. The producer's own `isRetryable` and
its callers are unchanged. A test requires the two to agree on every case. The
file has no string tags, `Any`, reflection, display copy, UI/data/runtime types,
or new retry/business/codec policy.

`NodeConfigDecodingException` stays separate. It does not implement the carrier
and has no payload family. A test checks all four of its cases.

The four producers keep their names, constructors, messages, `errorDescription`,
`toString`, raw fields, causes, `isRetryable` and caller behaviour. Each one
implements `SourceServiceFaultCarrier` with a covariant getter: an exhaustive `when`
over its own sealed class, with no `else` branch. The `RadioField` and
`CoordinateField` projections are private exhaustive `when`s in
`NodeConfigServiceTypes.kt`.

## Test adaptations

- **No Swift suites for the admin services.** Their 97 `WP-210::` cases are
  native and derived from the source. A real `MeshCoreSession` over `MockTransport`
  pins the wire bytes.
- **Real sessions where the source used one.** The teardown, CLI and other-params
  live cases use `MeshCoreSession` over `MockTransport`. The Swift live self-info
  packet was one byte short, and the Kotlin fixture uses the correct layout.
- **Fakes instead of SwiftData.** There is no SwiftData `Contact` model, so the
  type-byte test uses `ContactDTO`. Snapshot tests use an in-memory store with
  `DiagnosticRepository`'s logic and a clock that advances 1 ms per read. Key
  generation uses `Ed25519Crypto`, since `KeyGenerationService` isn't on this
  module's classpath.
- **Real paths instead of in-test copies.** Two "OtherSettings merge" cases
  computed the merge inside the test; they now exercise the real
  `importOtherParams`. The path-hash-mode import cases go through the planner.
- **Virtual time.** No test synchronizes with real sleeps.
