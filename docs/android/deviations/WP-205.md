## A-01: platform handles, activation and discovery

CoreBluetooth's peripheral UUID/cache/central-manager activation becomes an
immutable, `Locale.ROOT` uppercase Android connection-address handle and lazy GATT open. It never
becomes a persistent `radioID`, address-derived UUID or public-key identity.
Idle diagnostics have no peripheral/handle. Host selection, rotating-address
resolution, scanner/picker UX, CDM and system association belong to WP-206.
This component does not pretend to adopt another application's GATT.
`DeviceConnectedToOtherApp` remains a source typed case but is not guessed
from status133. Unsupported hardware is explicit `BluetoothUnavailable`, not
the source picker's collapsed transient-ready state.

## A-02: Android status and recovery

All fourteen source BLE error cases remain typed, with additional native
service/descriptor/property/MTU/frame/cleanup errors. Status metadata includes
its callback domain independently of any active operation. Android ATT
authentication/authorization/encryption/key-size status5/8/15/12 map to
`AuthenticationFailed`; generic statuses retain their operation, numeric code
and cause. Connection-state/HCI status8 (and Android's connection timeout147)
maps to `ConnectionTimeout`, even during a pending write/discovery; it must not
be reinterpreted as ATT insufficient authorization. The exact Nordic2.11.0
`GattError.parseConnectionError` versus `parse` implementations independently
establish this distinction. Immediate `BluetoothStatusCodes`, connection state,
RSSI measurements and callback ATT status are different domains.
Permission, adapter power and bond loss provide explicit
recovery. PIN entry and actual bond creation are system/host work, not a
hard-coded PIN, hidden call or automatic re-pair.

The pinned guide claims an individual CoreBluetooth `encryptionTimedOut`
is immediately an auth error, but actual pinned `ReconnectPolicy.swift`
classifies it through a retry majority/budget. Actual code governs. Android
does not infer an invalid bond from a silent operation or generic status133.
App-localized English/source descriptions are not inserted into the MIT
protocol production runtime; WP-304 supplies localized UI recovery.

## A-03: bounded discovery and ambiguous completion

Defaults preserve 10/40/15/5 seconds. Initial discovery's entire chain,
including actual MTU and CCCD completion, has one 40-second deadline; explicit
reconnect uses 15 seconds. Source policy can extend a connected-but-stalled
discovery twice and then infer auth failure. Native operations instead stop at
the configured deadline and report the actual timeout, not unproved bond loss.
Such extension/retry classification belongs to the WP-207 policy owner.

The source keeps the link after a write timeout and uses CoreBluetooth's
issued-write FIFO to tag late callbacks. Android callbacks lack that sequence.
Any submitted-operation timeout/cancellation/terminal failure therefore closes
and invalidates the GATT. If a deadline expires before facade invocation, the
unissued request still fails, its pending waiter is removed and timer is joined,
but a ready link remains usable because no ambiguous operation was issued.
Entering the facade counts as attempted submission even when it throws.
Startup/discovery timeout still closes incomplete setup, including before issue.
A new attempt waits for actual cleanup completion
and gets a new GATT/generation. Safe queued-call cancellation before issue does
not kill an unrelated active write. Owned timers are cancelled and joined;
only finite owned cleanup is awaited non-cancellably.

## A-04: generations, callbacks and streams

Source wall-clock disconnect timestamps have a one-second tolerance. Native
callbacks belong to a connection object created before `connectGatt`, with an
explicit generation; old GATTs/keys are rejected without a wall-clock guess.
Replies also match the original operation and exact characteristic/descriptor
objects. Synchronous callbacks are queued while the platform trigger is still
returning, so a false/nonzero start result cannot masquerade as success.

The source's data stream buffers 512 and ignores failed yields, errors and
empty values. Native immutable bytes queue every equal/empty/unknown packet
without conflation or silent overflow. The unbounded queue is an explicit
memory tradeoff requiring a continuous process/session drain. One active
collector is enforced rather than distributing ACKs among screen collectors.
Old streams terminate and retain accepted packets; failures remain typed.
Stream renewal over a stopped-but-live shared physical link is not fabricated:
session-owner reconnect/rebuild must deliberately acquire the new generation.

Hardware API callbacks have no public originating-operation ID. The facade
captures its one outstanding operation before each trigger and never reuses a
GATT after ambiguous completion. A pathological OEM duplicate callback with
the same GATT/attribute after a completed operation is not identifiable by a
newly invented Android sequence argument; physical callback reliability is
still a hardware scenario. Unsolicited MTU/service changes fail closed instead
of silently retaining invalid capabilities or calling hidden refresh.

## A-05: ATT versus firmware, write commands and pacing

See the [bounded Nordic source/API spike](../evidence/WP-205/nordic-spike.md).
The dependency-free native facade is a reviewed-candidate adaptation, not a
Nordic dependency admission or a claim its optional refresh always executes.
Actual API31/32 legacy field writes are copied immediately before issue;
API33+ immutable-value overloads preserve their returned status. API37 settings
disable auto-connect/automatic MTU. Actual callback MTU is checked; API34+
first-request-517 behavior is not mistaken for successful peer negotiation.

Commands are never split/truncated. Default bootstrap capacity is 20 bytes,
not an invented firmware maximum. Independently verified caller-provided peer
capacity is generation-scoped and immutable, bounded by actual MTU-3 and the
512-byte attribute limit. Larger unverified commands fail explicitly. The
component does not claim an integrated protocol startup handshake or radio
delivery from the debug APK.

Write commands/pipelined reads need their separate peer opt-ins and TX
properties. Without evidence the source-compatible fallback is acknowledged
send. Android's completion callback replaces CoreBluetooth's peripheral-ready
backpressure surface; both write routes are serialized through callback,
failure or timeout. Default pacing remains zero; explicit acknowledged pacing
applies to queued and sequential writes, while verified write commands skip it
as in the source. No arbitrary busy retries or pipelined GATT operations exist.

## A-06: reconnect/restoration ownership

CoreBluetooth's standing OS auto-reconnect, state-restoration adoption,
empty-GATT hold, foreground confirmation, five-failure majority and six-hour
bond grace are not portable Android GATT guarantees. The component performs
one explicit attempt, then surfaces success/failure and terminates old streams.
It neither starts an unsafe retry loop nor changes persisted manual disconnect.
`connect(Reconnect)` supplies the source's reconnect discovery budget when the
real owner requests a fresh attempt. Empty/partial success never publishes a
half-ready connection or preserves unproved OS reconnect registration.

`ReconnectPolicy.swift` is explicitly owned by WP-207 in the frozen manifest.
The original WP-205 retry/grace declarations are all retained in the source
accounting and mapped to the proposed no-implicit-retry platform adaptation,
not described as executed iOS-policy parity. WP-206/207/303 provide intent,
permission/background hosting and the real service graph. No unpublished
interfaces or fake connected UI are introduced to bypass that ordering.

## A-07: RSSI and bond refresh without fake persistence

Actual `readRemoteRssi` is an explicit queued native operation. A completed
nonzero RSSI status surfaces a typed failure and never refreshes verification;
it does not itself prove a dead bond. The RSSI callback deadline starts only after
operation-queue admission, like a write: two valid queued writes do not consume
an unsent RSSI request's budget or close a healthy connection. Acknowledged
pacing races its owned clock sleeper against connection termination and joins
the sleeper, so old-generation pacing cannot delay a replacement connection.
Source refresh-only, session-live and
existing-stamp guards are preserved using a stable radio UUID supplied by the
real identity owner and an injected wall clock. Disconnect clears live identity;
clear/reseed advances an epoch so obsolete persist hints fail revalidation.
Callbacks run outside the transport state monitor.

Android does not start the source's periodic iOS background keepalive or
promise it survives process death/force-stop; the real execution owner decides
whether to request RSSI work. In-memory refresh/reseed/forget guards do not
prove the source's `LastConnectionStore`/ConnectionManager persistence race.
The three consumer-bound bond declarations are explicitly marked
component-equivalent with process-store proof deferred in the case catalog.
WP-207/204 must retain their real storage epoch/transaction proof; a boolean
current-state check is not a transaction and cannot replace that gate.
