# WP-311: contacts and discovered nodes

Reference: `db14559b39d32322b06477c6ae676112f583db50`. Completion base:
`9b60b6965ce009e58517e8451f16f94502ae41f5` (current `origin/main`, including WP-316).
Owner role: `nodes-map-ui-engineer`. This completion increment builds on merged logic PR
#69 (`7e9584751ca79b874ced996e7056926bc3fc7ae8`) and adds the native Compose presentation,
production graph adapters and real URI/QR/camera/map integration. It is implementation
evidence, not an iOS, hardware or protected-gate approval.

Feature implementation remains in `android/feature/nodes`; directly necessary app assembly
adapters live in `android/app`. The feature still has no `core:services` edge. It adds only
`core:maps`, Activity Compose, CameraX and ZXing. Camera permission is optional, camera hardware
is not required, and the scanner always retains manual URI paste. Production adapters bind the
feature-owned seams to the process store and current per-connection service graph.

## Type placement (feature-owned seams and mirrors)

Feature modules cannot depend on `core:services`. Each consumed service is therefore a
feature-owned interface in `deps/NodesFeatureDependencies.kt`, which the app graph adapts.

- **T-1 `NodesDataStore`.** This is the subset of the main-branch `ContactPersisting` and
  `DiscoveredNodePersisting` contracts that these screens call. A narrow seam keeps the test
  doubles small. `NodesSession` keeps the source's two stores separate:
  `offlineDataStore()` (`AppState.offlineDataStore`, used by lists and discovery) and
  `servicesDataStore()` (`services.dataStore`, used by path editing, blocked contacts,
  refresh and import).
- **T-2 `NodesContactService` and `NodesContactFailure`.** These mirror the PR #49
  `ContactService` signatures. The adapter must map `ContactServiceError.contactNotFound`,
  `contactTableFull` and `shareContactUnavailable` to the three `NodesContactFailure` cases.
  `ContactServiceFault` exists only in PR #49, so it is not used.
- **T-3 `NodesAdvertisementService` and `NodesAdvertEvent`.** These cover the
  `pathDiscoveryResponse` and `traceSnrObserved` subset of `AdvertisementEvent`, plus
  `setSyncingContacts`.
- **T-4 `NodesTraceService`** stands in for `BinaryProtocolService.sendTrace`.
  **`NodesNotificationCleanup`** stands in for the two `NotificationService` calls made after
  clearing messages (WP-215/WP-401).
- **T-5 `ContactUriCodec` and `ScannedContact`.** `meshcore://contact/add` encoding is
  WP-209's (`exportContactURI`; PR #49 keeps `ContactUriBuilder` internal). Parsing and
  `ContactResult` belong to WP-405. The feature delegates both and re-implements neither.
- **T-6 `FirmwareTimeouts`** (WP-316 `FirmwareSuggestedTimeout`), **`UserFacingMessages`**
  (WP-304 `userFacingMessage`), **`Announcer`** (accessibility announcement) and
  **`StringListPreferences`** (the `UserDefaults` string arrays behind recent hops).
- **T-7 Local copies.** The feature keeps local copies of `RadioCommandTimeout.delete` (7 s,
  WP-304) and a clock-driven `withCommandTimeout`. It also keeps
  `DiscoveredNodeDTO.contactFrame()` (WP-304's `makeContactFrame`) and the
  `ContactType.localizedName` resource mapping. These should collapse onto the owners'
  versions when those land.
- **T-8 `NodesMessage`.** State holds typed `core:l10n` resource references and arguments
  instead of resolved strings, so no `Context` reaches the logic.
- **T-9 `path.PathHop`.** This is the editable hop with a stable id. It differs from
  `core:model.PathHop` (a display hop) and lives in a different package.

## Adaptations

- **A-1 State holders.** These replace `@Observable @MainActor` view models. Each holds a
  `MutableStateFlow`, an injected `CoroutineScope` and a `NodesClock`. They are confined to the
  main thread like the source. Properties that the source exposes as settable vars are set in
  tests through an `internal seed`.
- **A-2 Cancellation.** The source catch-alls sometimes swallow `CancellationError`, turning
  it into an error message or a `try?` nil. Kotlin always rethrows it. Cleanup still runs: an
  interrupted sync resets `setSyncingContacts(false)` and `isSyncing` under `NonCancellable`,
  and spinners are reset before the rethrow.
- **A-3 String semantics** (`text/SwiftText.kt`). Expectations come from `swiftc` oracles in
  [evidence/oracle](../evidence/WP-311/oracle):
  - `localizedStandardContains` and the picker's `[.caseInsensitive, .diacriticInsensitive]`
    use a per-grapheme fold: NFD, then nonspacing marks removed, then full case folding. A
    dotless `ı` is kept apart, and Turkish/Azeri fold `I` to `ı`. A match must start and end
    on folded-character boundaries. This reproduces Foundation for `ß`/`ss`, ligatures, Kelvin,
    Greek sigma, Hangul and `İstanbul` in `en_US`, no-locale and `tr_TR`.
  - Two known differences remain. Foundation with a locale matches fullwidth `１２` against
    `12`; Android does not. Foundation `localizedStandardContains` matches a member emoji
    inside a ZWJ family; Android does not.
  - `hasPrefix`, `Set<String>` de-duplication and name equality use NFC plus whole-grapheme
    comparison. `isHexDigit` accepts ASCII and fullwidth hex as single scalars. Fullwidth
    input then fails byte parsing, as it does in Swift.
  - `trimmingCharacters(in: .whitespaces)` trims Zs and tab, but not newlines.
  - `localizedCompare` and `localizedCaseInsensitiveCompare` use `java.text.Collator`
    (tertiary or secondary strength, canonical decomposition). This is ICU/CLDR on Android.
    The JVM test runtime uses the JDK tables, which agree on letters but order punctuation,
    spaces and some scripts differently. The owned cases use letters only.
- **A-4 Distance.** `CLLocation.distance(from:)` becomes great-circle haversine distance.
  Orderings only differ for near-equal distances.
- **A-5 Detail delete with no service graph.** The source's optional chain made this a silent
  "success" that dismissed the screen. Android reports
  `detail_error_servicesunavailable` instead of dismissing. The control is radio-gated in
  both versions.
- **A-6 Discovery countdown** uses the monotonic clock instead of `Date.now`.
- **A-7 Share sheet.** `ContactURIActivityItem` (an empty `String` placeholder, so iOS offers
  Copy) becomes a `text/plain` payload whose text is the URI (`ContactShareTextPayload`).
- **A-8 QR and camera.** QR rendering uses ZXing correction level M with fixed black modules
  on white so every unlocked theme remains scannable. CameraX analysis honors Y-plane row and
  pixel stride and closes every `ImageProxy`; permission denial exposes app settings while
  manual URI paste remains available. The QR output round-trips through ZXing in a JVM test.
- **A-9 Avatars.** The resize bounds (512 px longest side, JPEG 0.8) are ported as
  `AvatarProcessing.targetSize`. The completion UI does not yet expose a platform image picker;
  existing avatar data remains displayed by the detail logic and service seam.
- **A-10 Logging.** The source's `Logger`/`PersistentLogger` trace lines are omitted. The
  feature has no logging seam.
- **A-11 Maps.** Contact location uses the shared `MapLibreMapSurface`/OpenFreeMap provider,
  not a second map stack. The detail action can also route to the existing full map feature.
- **A-12 Production recents.** Recent hop order is stored as an ordered JSON string array in
  process `SharedPreferences`; a `StringSet` is intentionally not used because it would destroy
  LRU ordering.
- **A-13 Accessibility/adaptive UI.** Actions have explicit content descriptions, state changes
  use Android announcement events, and the existing WP-302 list/detail scene chooses tiled or
  single-pane presentation from current window size.

## Completion and remaining platform limits

- The two formerly deferred `ContactShareContentTests` cases now execute against the real
  `ContactService.exportContactURI` and `MeshCoreUriParser.parseContact` implementations.
- Compose lists/details/discovery, shared MapLibre location, CameraX scanning and QR rendering
  are implemented and compiled into the app.
- No camera hardware/device execution was performed locally; JVM QR decoding, Android lint,
  strict dependency verification and APK assembly are the claimed evidence.
- Avatar replacement remains unavailable because WP-311 has no admitted Android media-picker
  contract; the existing avatar service logic is preserved without manufacturing a picker.
