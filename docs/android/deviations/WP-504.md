benchmark. The deterministic Room/Compose timeline and local MapLibre renderer
are isolated component workloads, not replacement app features, captured user
data, original-case parity or hardware services. Main launcher startup remains
the actual app entry. The map workload deliberately excludes network provider
variability and does not claim production feature-map/offline-provider parity.

uses the R8-optimized, test-only `benchmark` variant. Both are independently
identified from the shipping package and use only ephemeral debug signing.
Ordinary release contains neither fixture routes/code nor a profileable overlay.
No release signing, account, billing, analytics, translation, updater or product
APK-installation behavior is added.

The instrumentation producer retains its existing Android-library plugin and
uses a distinct test-host package to exercise the external target. Actual
`BaselineProfileRule` collection does not need an extra Gradle plugin; generated
profiles must be admitted and embedded only after real collection. Required
Partial compilation fails without those profiles. This is not a fake profile
or an acceptance exemption.

reconciled WP-504's disjoint release-R8/profileable-target App keys and evolved
the same typed reservation in
[the ownership handoff on issue #137](https://github.com/cbattlegear/MeshCoreOne-Android/issues/137).

are changed here. Protected exact-head main-merge approval is still required.

`WP-504-behavior`, `WP-504-boundaries` and `WP-504-source-test-parity` are **not
accepted** by a successful build. Actual device/battery/ANR/16 KiB runtime,
collected/embedded profiles and measurement-derived budgets remain unverified.
The explicit optional build stage is local infrastructure admission, not a
canonical manifest/feature-acceptance receipt. See the
[runbook](../performance/README.md) for exact executable commands and limitations.

same WP-504 producer/reservation/PR. The existing WP-003 launcher provenance stays
intact. Advisory publication waits at most 10 seconds for the shared lane and
allows 180 seconds of exact-candidate fast execution, followed by owned-child
cleanup. These are tooling latency bounds, not measured Android performance
budgets. Queuing or timeout records the exact commit/tree as UNVERIFIED; it never
creates a successful verification receipt.

The Linux supervisor uses a child subreaper, libc pidfds and live ancestry checks
to clean only its own descendants, including detached children, while retaining
the inherited lane descriptor. Advisory Gradle does not reuse a persistent
Gradle daemon and runs Kotlin compilation in-process. Full/manual verification remains strictly serialized without
these advisory deadlines. Mandatory regression fixtures exercise the real
launcher with a test-owned holder, exact pending binding, timeout/detached-child
cleanup, manual serialization/failure and rejection of an absent inherited lock.
Fixtures are tooling evidence, not Android builds or device measurements.
Contributor adapters without supported owned-process supervision are explicitly
UNVERIFIED at publication rather than invoked unbounded; their exact full/manual
result validation remains available and unchanged.

Synchronize installed helpers only through the supported reservation runtime
installer after these regressions pass. Do not replace foreign processes,
manually edit installed helpers or remove an occupied lane lock.

## Opt-in application startup diagnostics

The existing Activity intent gate could not diagnose the earlier
`MeshCoreApplication.onCreate` widget/process/container startup work. A debug-only
build opt-in, `-Pwp504StartupStrictMode=true`, now enables the same detect-all,
log-plus-death thread/VM policies at the real Application entry, before its
super-call and that subsequent startup work. The runtime additionally requires
`FLAG_DEBUGGABLE`. The property defaults to false and rejects non-Boolean input;
release/profile/benchmark resources stay false regardless of that property.
No generated BuildConfig, dependency, new variant, diagnostic framework, runtime
intent/preference toggle or shipping product affordance is introduced.

The boundary deliberately excludes the Application constructor/field initializers,
context attachment, earlier provider initialization and Android/zygote/framework
startup. Thread policy covers the calling main thread; VM policy is process-wide.
The original WorkloadActivity intent gate and its penalties remain unchanged.
No policy exception or swallowed violation makes a diagnostic launch successful.
No startup-clean/device/ANR/battery/profile/budget acceptance is implied.

The new API31/API37 Robolectric family invokes the actual MeshCoreApplication
entry and observes policies at the intercepted Application super-call, stopping
there before widget/container side effects. Moving installation below that
boundary fails the ordering assertion. Both policy masks must match independent
detect-all/log/death builders; disabled and nondebuggable inputs must preserve
pre-existing policies rather than reset them to lax. A normal-debug resource
control verifies default-off configuration. Test cleanup restores host-sandbox
policies only; production penalties are not reduced or suppressed.

This bounded software change preserves the merged301 fixture entries and foreign
WP-503 assertion work. Same-owner trusted App support evolution/readback is
revision16; immutable source/identity/authorization/history stay intact.
No runtime/hooks/SDK/key installation, endpoint allocation, ADB/emulator/guest,
physical or profile collection is part of this correction.
