# WP-101 protocol value and byte foundations

The pure JVM module implements the owned byte/model/configuration/transport
surface against reference `db14559b39d32322b06477c6ae676112f583db50`.
It does not implement a radio session, packet parser, crypto exchange or UI.

| Source behavior | Kotlin adaptation |
| --- | --- |
| `Data` value equality and copy semantics | `Bytes` copies inputs/outputs and compares/hashes contents; diagnostic text does not expose key bytes |
| Binary read helpers returning zero on short data | Original helper semantics remain, separately from `ByteReader`, which throws a typed truncation error without advancing |
| Swift `Character` UTF-8 limits | Java's extended-grapheme `\X` segmentation preserves combining accents, ZWJ families and flag pairs; tests also cover CJK and four-byte emoji |
| Pairwise protocol hex initializer | Keeps source odd-tail truncation and Swift unsigned-number sign behavior; invalid complete pairs remain a failable parse |
| Services' formatted hex initializer | Explicit test-only adapter filters hex digits and rejects odd filtered lengths; it does not replace the protocol parser or enter the MIT production artifact |
| Swift 64-bit `Int` values | Device/storage counts and configuration window values use `Long`; small packet offsets/sizes remain checked JVM array indices |
| Actor-isolated transport getters | Suspended Kotlin methods preserve capability/getter ordering; receive data is a terminating, per-connection `Flow`, not a conflated state or uncloseable broadcast |
| Mutable `OtherParamsConfig` value struct | Immutable configuration plus `copy`, preserving all six values without sharing mutable state |
| Error enum payloads | Typed exception cases retain raw device codes, command/reason, size, prefix and cause metadata |

## Negative path hop count (issue #375)

The pinned `encodePathLen` source validates `hashSize` with a precondition, clamps
`hopCount` to `maxHopCount`, then converts that value to `UInt8`. A negative
`hopCount` therefore traps during the unsigned conversion; the source API does
not return a result or expose a recoverable typed error for this invalid input.
The pinned `DecodePathLenTests` covers valid hash sizes and explicitly notes the
un-testable hash-size precondition cases, but does not define a negative-hop
error contract or include a negative-hop test.

The Android utility preserves the supported wire behavior and rejects
`hopCount < 0` with `IllegalArgumentException` before packing. This is an
explicit native fail-fast adaptation, not a claim that the Swift trap is a
typed error and not a change to valid encoding: values `0..63` encode normally
and values above 63 retain the source clamp. `PathEncodingTest` now isolates
the negative boundary in its own assertion, separate from invalid hash sizes.
This supplemental adaptation test does not add original-family credit or
prescribe reproducing a Swift process trap.

Production consumers derive hop counts from nonnegative path lengths; the
session path-update boundary also validates hash size and complete hash chunks
before encoding. The negative case therefore characterizes direct misuse of
the public encoding helper rather than a newly established normal-input
failure.

The library preserves the default `MeshCore-Swift` client identifier; an Android
application can explicitly select its client identifier when wiring its session.
No default was silently changed at the wire/library layer.

`MessageResult` from the same Swift configuration file requires the event/message
payload vocabulary. Its associated-value declaration is intentionally integrated
with that vocabulary in WP-106/107, not replaced here with fake payload classes.
The source file header accounts for the configuration/error declarations, not an
assertion that the entire application or every declaration is finished.

The coroutine runtime uses the existing `1.10.2` version pin. Exposing the `Flow`
contract requires its JVM API dependency and consistent transitive Android
runtime locks. Three previously unrecorded publication POMs were checked against
Maven Central's published SHA-256 files and added without changing version pins
or disabling strict verification.

The production Kotlin implementation adapts only the MIT MeshCore sources; the
existing module MIT notice remains present. The formatted display adapter is
adapted from the GPLv3 application service extension, is confined to test sources
under the repository's GPLv3 terms and is absent from the production artifact.
Its production counterpart belongs to the application's services, not this
standalone protocol port.
