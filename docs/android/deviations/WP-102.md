## Exact native contracts

| Concern | Pinned Swift behavior | Kotlin behavior and consequence |
| --- | --- | --- |
| Immutable data | `Data` has value semantics | Reuse existing content-equal, defensive-copy `Bytes`; no second byte wrapper |
| Channel results | Success with `UInt32` timestamp, `UInt8` type and nonoptional text; three failure cases | Immutable sealed `DecryptResult`, `UInt`/`UByte`, and the same three failure cases; equality is content/value based |
| Direct results | Five outcome cases; authenticated invalid UTF-8 yields success with timestamp and **nil text** | Preserve all five outcomes and nullable text, including timestamp extraction from an authenticated invalid-text result |
| Secret sizes | AES takes the first 16 bytes of any secret of at least 16 bytes; HMAC uses **all** bytes | Same behavior, including 17/24/31/32/33/64/65/128-byte independently specified secrets; do not restrict to 16 or 32 |
| Empty HMAC key | CryptoKit HMAC accepts RFC2104 key normalization | JCA rejects a zero-length `SecretKeySpec`; use its mathematically identical zero-filled SHA256 block only for the empty HMAC key. Raw AES still rejects secrets below 16 bytes |
| Authentication | Source compares two-byte `Data` tags | Use vetted BC `Arrays.constantTimeAreEqual`, preserving the exact leading two-byte tag, key and ciphertext-only authenticated region |
| Provider errors | Source AES helper returns nil and ECDH catches key-agreement errors | Known malformed sizes/low-order peers keep source decrypt outcomes. Actual JCA provider/algorithm failures are explicit `CryptoException.ProviderFailure`, not a fake authentication/decryption result or success |
| Ed public-key failure | Source returns nil for non-32-byte input; its handwritten field helper does not validate 32-byte points | Native conversion throws typed size/point failures. Validate a canonical, non-identity prime-order Ed25519 public point with BC before applying the original birational map using BC field operations |
| Expanded private keys | Firmware exports `[expanded_scalar:32][nonce:32]`; key generation hashes a seed with SHA512 and clamps its scalar | Distinct named seed/expanded APIs. BC `expandPrivateKey` returns unpruned SHA512; explicitly use its vetted `ExpandedKey.prune` before exporting a generated firmware key. Derive/sign through `ExpandedKey`. Validate source clamp constraints instead of silently fixing imported malformed keys |
| Private Ed-to-X conversion | Source RxLog takes the first 32 expanded bytes, not a new hash of those bytes | `x25519PrivateKeyFromExpanded` validates 64-byte expanded input and returns its first 32 bytes. `x25519PrivateKeyFromSeed` performs the source SHA512 expansion exactly once |
| Local signing | Source protocol session delegates start/data/finish signing to the radio | WP-102 supplies real local RFC8032 primitives, including expanded-key signing. It does not pretend to implement radio signing/session operations owned by WP-107 |
| Diagnostics | Source success enums can carry text | Kotlin successes retain equality/fields but format diagnostic strings with text length, not decrypted content |

**User-approved domain decision (2026-10-27):** Android keeps strict Ed25519
point validation. The pinned Swift converter returns `nil` for non-32-byte
inputs, but otherwise applies the map without validating the point. Android
preserves the rejection boundary while making failures explicit:
`InvalidKeyLength(ED25519_PUBLIC, actual)` for non-32-byte input and
`InvalidEd25519PublicKey` for malformed, non-canonical, identity, or
non-prime-order 32-byte encodings. This is an intentional Android adaptation;
valid canonical public-key bytes and the conversion formula remain unchanged.

The original 0-byte/16-byte family maps to exact typed size-error assertions;
new focused assertions pin the strict malformed-32-byte policy. Independent
valid-key vectors exercise converted public keys, both ECDH directions and the
converted-key direct-message path. `RxLogEntryDecryptor` retains its existing
catch-and-omit behavior for invalid contact keys, matching the source optional
conversion at that cache boundary; the converter itself never collapses those
failures to a successful or fabricated key.

The real dependency API probe rejected unpruned expansion bytes against the
independent firmware vectors. Inspection of the exact publisher source confirmed
that BC expansion deliberately leaves pruning to its callers/on-use methods.
The native generation adapter now prunes once before export; it never prunes a
malformed **import** to hide an invalid key. Expected vector bytes were unchanged.

## Intentionally unchanged behavior

AES is **AES-128/ECB/NoPadding**, with zero-extension only in the source-equivalent
encryption primitive. A complete input block gains no extra block. Decryptors
stop text at the **first NUL**; arbitrary bytes after that NUL are not a padding
error. Channel invalid UTF-8 fails; direct invalid UTF-8 preserves a genuine
authenticated timestamp and nullable text. No longest-valid-prefix or
replacement-character decoding is substituted.

Payload minimum checks precede authentication/key derivation exactly as in
source. Authentication precedes block-alignment failure. DM key derivation
precedes authentication. DM destination/source hash bytes are not authenticated
by this source scheme. The two-byte MAC has its source security limitations;
this is wire compatibility, not an AEAD upgrade or at-rest encryption.

These APIs are stateless synchronous primitives, as in the original enums.
There are no sessions, waiters, streams, background scopes or cancellation
catches. Structured cancellation/timeout/correlation behavior remains WP-107;
no asynchronous crypto cancellation or radio certification is claimed.

## Dependency and platform boundary

The exact inspected candidate is `org.bouncycastle:bcprov-jdk18on:1.86`, with
MIT artifact notice, no POM dependencies, Java8 base bytecode and an actual
vetted `Ed25519.ExpandedKey` API. No Android security provider is installed or
replaced. Production protocol APIs expose only existing `Bytes` and Kotlin
values, never BC classes or `core:testing`.

The shared dependency wiring amendment is now explicitly authorized and
serialized after WP-005 released its XML lease. The initial missing-dependency
failures remain genuine historical evidence, not successful tests.
The kickoff's semantic policy revision was correct: `gates.policy_revision`
includes manifest/source and excludes operational switches, so it differs
from the canonical JSON file digest. This distinction is independently checked
and documented without advancing a pin or modifying paused automation.

JVM results, JAR API inspection and later Android packaging do not certify
physical API31/API37 devices, firmware, radios, legal release approval or
signing. Keystore/vanity identity generation is WP-204; remote signing is
WP-107; dependency notice/distribution review remains the actual owning gate.
