## A-01: process adapters and the future service graph

`ConnectionManager` consumes the merged JVM session, neutral device/contact/room
repository contracts, and narrowly injected process preference, platform and
service-factory roles. Runtime production has no Android, database, DataStore,
BLE implementation, testing, service or feature dependency. Factory allocation
must register an owned service handle before suspension and separately register
partial children for reverse-order cleanup. `RuntimeServices` extends the
existing neutral `SessionServices`; only tests implement the graph here.
WP-303 must supply concrete adapters and the real WPs 208-218 service graph.

Callbacks are installed before the session activates its physical transport.
UI state, transport state, intent and generation are distinct. Sync failure
remains `SYNCING` with a typed issue, never a successful empty graph or `READY`
send-drain state. Process repository/preferences are not closed by a radio
generation. The process launch invokes the real global remote-session reset;
the Apple's historical random-ID/sort-date/flag migrations are not rerun against
native v1 data.

## A-02: physical renewal, not a fabricated retained-link generation

Swift reconnect stops the old session without disconnecting, re-vends the
same connected BLE data stream, and keeps the phase's RSSI keepalive. The merged
WP-107 JVM session deliberately rejects a new session on a retained physical
link because untagged late responses can satisfy a newer request.

The runtime can retain one physical lease during a bounded recovery episode,
with ingestion and service scopes stopped. It must physically close that lease
before a new session is started. This is a changed native safety policy, not a
claim that Android supports Apple's retained stream renewal or RSSI behavior.
The three original BLE stream-renewal families are replaced by real-session
retained-admission refusal, old-reader completion, physical-close and fresh
ordered-stream assertions. A retained receipt alone is never fresh connection
evidence. Explicit user disconnect closes immediately and suppresses recovery.

## A-03: stable first-contact identity

Existing device/public-key records, including restored arbitrary UUIDs, keep
their partition identity. A first-contact partition uses the already-merged
`DeviceIdentity` helper: the first 16 raw SHA-256 bytes, without rewriting UUID
version/variant bits. Swift's random UUID fallback is intentionally not used.
BLE addresses and registry UUIDs remain endpoint handles, not radio identity.
Native Bluetooth endpoints are not written as fake legacy Apple
`ConnectionMethod.Bluetooth` values. WiFi descriptors retain source semantics.

Identity imports invoke the actual ghost-reconciliation repository method and
remove the retired derived V-contact. A live graph's radio partition is
immutable: a changed partition requests a guarded rebuild rather than retagging
an existing send drain.

## A-04: cancellation and errors

The source FIFO semaphore has no queued cancellation cleanup. The native
semaphore removes cancelled waiters and compensates a granted permit cancelled
before resumption. Deadline races still join both children, including
cancellation-ignoring cleanup; typed timeout and cooperative cancellation are
distinct. The foreground/suspending deadline clock is injected separately from
elapsed-time retry/UI clocks; no claim about Android suspension/FGS policy is made.

Source best-effort storage paths are not replaced by missing data or unconditional
success. Required storage/factory failures propagate with typed causes;
independent maintenance failures and cleanup issues are explicitly reported.
The deadline race transports an exception as a result value before rethrowing,
avoiding coroutine debug stack recovery replacing the original error object.
Multicast queues close normally and drain before rethrowing their stored terminal
cause. UI `StateFlow` is not used as an ACK/transition queue.

## A-05: platform capabilities

CDM pairing, scanning, permission prompts, execution-host/FGS policy and Android
GATT/network binding are external injected capabilities owned by WP-206/303.
Apple pending-connect/discovery decision tables retain their pure policy
behavior, but do not invent Android indefinite auto-connect or silently call a
placeholder adapter. Public failure projections keep auth/timeout/status roles
separate; there is no Android platform import in runtime.

## A-06: shared attempts have one authoritative caller

Equivalent submitted calls share one real session/service attempt, including
the interval before its first diagnostic reporter returns. A coalesced caller
is an observer: cancelling it propagates to that caller only. It cannot cancel
the shared operation, clear its pending slot, close its graph, or publish a
terminal connection state. Owner cleanup and slot edits require the original
submission revision and task identity.

Diagnostics remain fallible and their actual exception is returned to the
authoritative caller. If another observer has already completed the shared
operation successfully, a late reporting failure preserves the live generation,
READY token, ingestion reader and monitors. Otherwise the owner cancels/joins
the failed attempt and closes only that attempt's generation before terminal
publication. An obsolete reporter cannot affect a successor revision.

The native cases separately pause the real AppStart handshake and cancel a
coalesced observer, and pause both the first reporter and the coalescer's final
continuation after a completed READY operation. Default-dispatcher test callers
are test-owned; finally blocks release barriers before non-cancellable joins.
The paused handshake has already reached source `CONNECTED` transport state,
not READY: it has no session token or enabled send drain. The observer test
asserts the complete snapshot remains unchanged, as well as the authoritative
caller's live pending slot, reader and eventual single READY graph.

## A-08: uncertain correlation is a runtime-owned physical loss

The existing WP-107 `SessionDiagnostic.CorrelationUncertain` signal extends
A-02's native late-reply safety adaptation. Swift has no equivalent quarantine
notification: this is not a claim that Swift reconnects on an unmatched channel
query. Previously runtime consumed background failures only, leaving a healthy
looking READY graph whose channel/error response families were permanently
fenced after a genuine query timeout or cancellation.

The runtime now enqueues that existing public signal on a separately injectable
dispatcher (`Dispatchers.Default` in production), outside the producer's
protocol-lock stack. At execution it checks the captured runtime owner, not the
session-local generation number (which can restart at one). One atomic loss
claim withdraws the live token and fences retired callbacks; physical teardown,
service teardown and loss notification coalesce. The snapshot carries the
typed `ConnectionLost(UnresolvedReply)` cause. Neither the original caller's
timeout/cancellation nor SessionCore's unresolved-response fences are changed.
The existing best-effort auto-add timeout case retains all its original
default-config/reporting/retry-budget assertions under a gated recovery
dispatcher, then additionally proves physical renewal when the queued signal
runs. Best-effort fallback is not permission to keep an uncertain link forever.

Recovery uses existing source-derived policy: BLE waits for the foreground
watchdog's 30-second first health check, respects pairing/background deferral,
and uses the normal connection attempt/backoff/breaker; WiFi uses its existing
immediate loop/window/cooldown. A user stop, newer generation or shutdown
invalidates asynchronous continuation, including after a suspended physical
close or loss observer. READY requires the replacement's real handshake and
successful initial sync, never merely dispatching a callback.

`CorrelationRecoveryTest` exercises the real MeshCoreSession over deterministic
wire-frame fakes, including unmatched ERROR 2, blocked repeat queries, physical
close, complete state order, fresh successful query, pipeline diagnostic
coalescing, late frames/callbacks, manual stop before/during teardown, written
versus unwritten query cancellation, replacement, WiFi cooldown and process
cancellation. Existing original cases are retained. The test graph is the
approved fake factory, not the later App/messaging graph.

The initial repair changed no protocol, messaging, contracts or App paths. WP-208's
per-envelope failure progress across graph replacement remains a separate
producer/consumer integration prerequisite; WP-303 does not need a new runtime
constructor argument because the recovery dispatcher has a production default.
The subsequently identified accounting-ordering prerequisite and admitted App
support are recorded in A-09; physical recovery alone is not whole-bug acceptance.

park, persistence, wire and cleanup assertions. A thread-safe test dispatcher
defers physical recovery until those assertions finish, then verifies one
physical close, zero readers/jobs, withdrawn token and retained typed failures.

literal-three-second B-survival witness. No delay, fabricated cancellation
credit or default-success lifecycle hook is introduced here.

## A-10: admitted query accounting precedes correlation teardown

WP-208's published queue completion observation supplies the previously missing
producer contract. Runtime now requires
`RuntimeServices.awaitChannelQueryAccounting()` and coalesces one owned
observation before awaiting it outside protocol/runtime locks. The live token
and snapshot remain unchanged until admitted query accounting, park or terminal
persistence has completed. Only then does the existing loss path withdraw the
token and retire the physical generation.

Manual stop, replacement, shutdown or an independent physical loss cancels the
observation without waiting for an indefinitely parked drain. An identity check
after suspension prevents old completion from retiring a successor. A cancelled
producer observation while its runtime generation remains current does not
prevent physical recovery from the genuine correlation diagnostic; no query
failure is inferred or credited by runtime. Runtime caller cancellation
propagates, and non-cancellation observation failures are reported explicitly
and retained as suppressed causes of the original correlation failure.

The graph port is mandatory, not a default-success hook. Its concrete queue
delegation belongs to WP-303. Six additional real-session/fake-graph cases assert
accounting-before-token-withdrawal, coalescing while suspended and every
invalidation/error outcome. Disjoint data/connectivity test-double compatibility
was admitted under the same reservation's revision 3; no primary persistence,
BLE or messaging implementation is changed.

The inherited BLE retry timing remains unchanged. Neither this ordering repair
nor gated supplemental execution establishes the ungated App/Room A-terminal /
B-three-second-survival witness or resolves the original 30-second A deadline
against the 30-second BLE watchdog. Those remain combined acceptance blockers.

## A-11: frozen query-timeout fixture and unresolved native timing contract

At the unchanged source pin, the per-envelope counter case in
`ChatSendQueueServiceTests.swift:372-463,606-745` connects a simulator transport
and dispatches typed ERROR 2 events directly to subscribers. This bypasses the
transport/parser (`MeshCoreSession.swift:496-500`). The channel query requires
`channelInfo` for its index; unrelated errors are ignored until timeout
(`MeshCoreSession+Channels.swift:18-22`,
`MeshCoreSession+EventWaiting.swift:90-117`). Its genuine query failures are
timeouts, not ERROR 2 converted to channel-not-found or null. That fixture has
no connection manager or physical-generation retirement.

The full-App/raw-parser witness additionally exercises A-02/A-08's native
physical recovery. Its continuously foreground Bluetooth scenario has no
automatic faster driver than the existing 30-second watchdog. A real Activity
foreground edge can invoke immediate health reconciliation, including one
one-second activation fallback. A genuine CDM appearance can request a normal
connect. Neither event is generated by correlation-triggered physical close.
Android BLE supplies no implicit OS auto-reconnect here, and the queue's
`transportDidOpen()` only signals an already-ready owner; it cannot create a
physical generation. Synthesizing those events per failure would change the
fixture rather than prove its unchanged lifecycle.

Thus unchanged recovery timing cannot establish two genuine A failures within
the original total 30 seconds and B's genuine first failure within the following
literal three seconds. An untouched offline B row is not sufficient evidence.
The source-only investigation does not approve an adaptation: a distinct,
revision-fenced protocol-reset reconnect driver or a native timing-acceptance
deviation requires explicit reconciliation. No retry constant, deadline,
clock, response matcher, quarantine or query outcome is changed by this record.
