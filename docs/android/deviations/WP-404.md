# WP-404 deviations

| Area | Adaptation | Observable behavior |
| --- | --- | --- |
| App Intents / Siri | iOS App Intents and the `AppShortcutsProvider` have no Android equivalent. Android uses dynamic launcher shortcuts (`ShortcutManager`) for status, zero-hop advert, flood advert and one send shortcut per recipient, plus an exported `ACTION_SEND` `text/plain` share target. Static shortcuts and the direct-share XML are not wired because that requires `android.app.shortcuts` meta-data on the app launcher activity, which WP-404 does not own. | Same three actions (send, status, advert) are reachable from the launcher and the share sheet. Voice phrases are not ported. |
| Authorization | iOS `requestConfirmation` / `authenticationPolicy` become a platform-owned `ShortcutConfirmationPort`. Every send, and every flood advert, requires an explicit positive confirmation naming the recipient/reach; a declined or cancelled confirmation queues nothing. A zero-hop advert (the Swift default) runs from the user's own shortcut tap; status is cached read-only. Shared text is never sent without confirmation. | Preserves "never send under the user's identity without a deliberate act". Flood-advert confirmation is stricter than Swift, which did not confirm adverts. |
| Radio selection | Target ids keep the Swift `<radioId>/<kind>/<key>` scheme (contact public key, channel secret digest, never the raw secret). Ids are re-resolved against the live radio; other-radio, stale, unknown, ambiguous (duplicate channel digest) and malformed ids fail safe. A radio change or drop during confirmation escalates to the foreground instead of queueing. | Messages cannot be queued to a radio the user did not choose. |
| Module boundary | ModuleGraph allows `platform:shortcuts` only `core:model`, `core:contracts` and `core:l10n`. The Swift `IntentBridge`/`AppState` reach is replaced by ports declared in the module (`ShortcutRadioPort`, `ShortcutConfirmationPort`, `ShortcutText`, `ShortcutPresenter`); the app supplies implementations over its services. | No dependency on `core:services`. |
| Cold start | `ShortcutDispatcher` holds a single request until the app installs its handler, delivers it once, and drops it after five minutes. Holding is not authorization. The share target launches the app when no handler is installed. | Mirrors the WP-405 pending-route contract. |
| Limits | Shared text is capped at 4096 chars, only `text/plain` is accepted, blank/oversized/unknown input is dropped. Direct messages are length-checked (150 bytes) before confirmation; Swift deferred that to the message service. | Invalid input is rejected before any confirmation prompt. |
| AppFunctions | Alpha AppFunctions is not used and is not a release prerequisite. | None. |

Not delivered here (outside the WP-404 write paths, tracked as deferred integration): the app-side
implementations of the ports, calling `ShortcutHost.dispatcher.install(...)` and
`ShortcutPublisher.publish(...)`, referencing `res/xml/wp404_share_targets.xml` from the launcher
activity, the recipient-chooser/compose UI for shares without a chosen recipient, and the
confirmation UI. Device verification was not performed.

## Bounded session-error follow-up for #217

The original enum-only error model lost Swift `IntentError.sessionError(MeshCoreError)`.
The follow-up adds a sealed payload-bearing `ShortcutError.SessionError` retaining the
actual `MeshCoreException`, independently of the outer diagnostic cause. Localization
uses the existing pinned generated core:l10n resources, including typed format arguments
and firmware-code mapping; no English diagnostic message substitutes for those keys.
The platform module cannot depend on core:ui/services, so it resolves this narrow
MeshCore presentation mapping locally rather than adding a forbidden production edge.
The App service-wrapper mapping remains with the WP-502 producer.

Five new actual unit methods cover the owned payload/presentation contract, with real
compiled resources across all 12 shipped locales. This supersedes the historical
localization-test exclusion only for the session-error recursion/no-own-key families;
it does not claim that all metadata/framework tests or full-WP acceptance are now complete.
See the new dated evidence section; prior PR #151 evidence remains historical.

## Shortcut consumer repair batch (2026-10-26)

Bounded groups RADIO-R118-G06/G07/G08/G10 bind the existing shortcut contracts to
their actual App consumers. The picker and dynamic publisher receive one
`AppShortcutRadio.targets` list built by `SendRouting.buildTargets`; duplicate
channel digests remain ambiguous even when one slot has no display name.
The existing cached `LastConnection.deviceName` supplies connecting/offline status,
without making it a live node name or inventing a battery reading.

If the selected radio remains operational but its services disappear before any
pending-message write, the adapter raises the narrow typed
`ShortcutServicesUnavailableException`. `SendMessageFlow` converts only that
condition to `NeedsForeground`; the executor shows foreground recovery and retains
the original request. Disconnected, foreign-radio, service failures and cancellation
keep their existing distinct behavior. No new connection owner or background
reconnect policy is introduced.

`ADVERT_FAILED` now uses existing `error.advertisement.sendFailed` localized copy,
not message-enqueue copy. Session payloads and outer diagnostic causes are unchanged.
The preceding original integration/deferment notes are historical, not a claim that
these current App bindings remain absent.

Product verification for this batch is **BLOCKED / UNRUN** by the coordinator's
capacity/serialized-runner hold. Source and regression methods are authored only;
no device, hardware, full-WP or passing original-case acceptance is claimed.
G09 pre-advert GPS policy is explicitly outside this batch.
