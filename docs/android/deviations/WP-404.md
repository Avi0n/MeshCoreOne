# WP-404 deviations

## RADIO-R118-G09: shared callback-cache successor, not yet verified

The shared-cache source successor restores the pinned app-wide ownership:
one initially absent immutable coordinate lives on the existing process-owned
`LocationManagerLocationProducing`. A successful callback publishes it under
the active-request lock, before resuming the waiter. Failed/null fixes and
authorization denial retain the previous success. Cancelled, stale or closed
requests cannot publish a replacement.

The factory supplies a read-only getter from that same producer to the advert
helper. Region resolution and adverts still use distinct `LocationService`
wrappers, but a successful fix obtained through either wrapper is shared.
PHONE refresh failures and the unauthorized no-prompt branch can reuse that
coordinate; with no prior fix they retain the existing best-effort no-write
advert behavior. No shortcut-private cache, OS last-known lookup, expiry,
persistence, provider, permission or Google dependency is introduced. Existing
per-device/public policy, confirmation, current-session and cancellation gates
remain in front of writes and adverts.

This source work follows the actual failed `3db4cbd5` closeout and trusted-main
PR #356's eight-path named-operation admission. It is not a cache/native parity
PASS: the successor's declared execution is **NOT RUN**. The first 17-method
run failed five assertions. The native cache and cross-wrapper consumer cases
must pass in a separately admitted exact-candidate closure before G09 completion.
G18 remains a distinct bounded correspondence concern, not coverage supplied by
this source change.

## Historical initial G09 fresh-fix candidates

This successor to merged PR #350 activates only the previously omitted G09
consumer. The prior batch's G09 exclusion and NOT RUN notes below describe that
historical batch, not a restriction on this separately assigned concern.

The actual shortcut advert adapter now reads the selected device's existing
persisted auto-update/source snapshot. No device, public-location policy zero,
or the default per-device opt-out performs no refresh. With an enabled,
permitted policy, DEVICE reads/enables/verifies the radio's existing GPS setting;
PHONE obtains a fresh fix from the already installed process-owned framework
`LocationManagerLocationProducing` and uses `SettingsService.setLocationVerified`.
Both finish before sending the existing zero-hop/flood advert. The existing
flood confirmation remains before any location preparation.

Shortcuts never request permission. A narrow `LocationProducing` wrapper rejects
the orchestration service's permission-request branch with its existing typed
`NotAuthorized` error. The production binding first refreshes actual OS
authorization; it adds no provider, permission, Google dependency or location
cache. Existing coarse authorization is sufficient to attempt the existing
producer, not a claim that background location is available on a physical device.
Source-compatible location/settings refresh failures warn by error type, without
raw coordinates/firmware diagnostics, and then permit the advert. Genuine
coroutine cancellation propagates and sends nothing. Missing production policy
wiring fails instead of silently bypassing an enabled refresh.

The pinned Swift helper can fall back to `locationService.currentLocation`.
The accepted Android producer has no cached-location contract (also recorded in
WP-313). This change does not invent one, call an OS last-known-location API,
or claim cached-fallback parity: an unavailable/unauthorized fresh phone fix
leaves radio coordinates unchanged and continues the advert. Any requirement
to add cached-location availability remains an explicit missing operation, not
proof that a new provider/permission is authorized.

Native asynchronous reads/fixes also require the original live session and
device before any settings write/advert. A later opt-out or public-policy
revocation suppresses the coordinate write; a lost/replaced session raises
the existing typed not-connected outcome without sending through the old graph.
These guards do not redesign reconnect ownership or G18 lifecycle/metadata.

The G09 source candidate adds deterministic real App/Room/protocol and native
location regressions; Android execution is **NOT RUN** until a supported,
exact-candidate guarded job actually completes. No hardware/iOS result is claimed.

## Bounded session-error follow-up for #217

The original enum-only error model lost Swift `IntentError.sessionError(MeshCoreError)`.
The follow-up adds a sealed payload-bearing `ShortcutError.SessionError` retaining the
actual `MeshCoreException`, independently of the outer diagnostic cause. Localization
uses the existing pinned generated core:l10n resources, including typed format arguments
and firmware-code mapping; no English diagnostic message substitutes for those keys.
The platform module cannot depend on core:ui/services, so it resolves this narrow
MeshCore presentation mapping locally rather than adding a forbidden production edge.
The App service-wrapper mapping remains with the WP-502 producer.

Five new actual unit methods cover the owned payload/presentation contract, with real
compiled resources across all 12 shipped locales. This supersedes the historical
localization-test exclusion only for the session-error recursion/no-own-key families;
it does not claim that all metadata/framework tests or full-WP acceptance are now complete.
See the new dated evidence section; prior PR #151 evidence remains historical.

## Shortcut consumer repair batch (2026-10-26)

Bounded groups RADIO-R118-G06/G07/G08/G10 bind the existing shortcut contracts to
their actual App consumers. The picker and dynamic publisher receive one
`AppShortcutRadio.targets` list built by `SendRouting.buildTargets`; duplicate
channel digests remain ambiguous even when one slot has no display name.
The existing cached `LastConnection.deviceName` supplies connecting/offline status,
without making it a live node name or inventing a battery reading.

If the selected radio remains operational but its services disappear before any
pending-message write, the adapter raises the narrow typed
`ShortcutServicesUnavailableException`. `SendMessageFlow` converts only that
condition to `NeedsForeground`; the executor shows foreground recovery and retains
the original request. Disconnected, foreign-radio, service failures and cancellation
keep their existing distinct behavior. No new connection owner or background
reconnect policy is introduced.

`ADVERT_FAILED` now uses existing `error.advertisement.sendFailed` localized copy,
not message-enqueue copy. Session payloads and outer diagnostic causes are unchanged.
The preceding original integration/deferment notes are historical, not a claim that
these current App bindings remain absent.

Product verification for this batch is **BLOCKED / UNRUN** by the coordinator's
capacity/serialized-runner hold. Source and regression methods are authored only;
no device, hardware, full-WP or passing original-case acceptance is claimed.
G09 pre-advert GPS policy is explicitly outside this batch.
