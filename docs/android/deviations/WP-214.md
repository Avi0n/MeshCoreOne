# WP-214 sync coordinator and sync retry adaptations

Reference: `db14559b39d32322b06477c6ae676112f583db50`. Base: `main` @ `7237727f`.
**External contribution:** prepared outside the dispatch controller, with no lease,
session or receipt. These are proposed adaptations for coordinator review. All code
is pure JVM in `core/services/.../services/sync/`.

## Current suppression/smoke oracle repair

The original suppression families now retain the source's actual notification
service true precondition and final false assertion instead of substituting only
a fake flag. A test-only suppression bridge connects that real service in the
pure-JVM suite; additional App integration uses the real production adapter.
A gated poll's intermediate true observation is a newly authorized native oracle,
not retroactive Swift assertion credit.

Likewise, native message-delivery and monitor cancellation/join/replacement
assertions supplement, rather than relabel, the original wiring/monitor smokes.
Disconnect now has a non-Idle precondition. A reversed sender-timestamp pair
separated by six seconds supplements the original already-sorted input and
detects erroneous global sorting. The original resync begin/disconnect assertion
still proves no end callback at disconnect, not double-end prevention. No
production activity-order, retry-owner or timestamp-range policy changes result.
These cases are authored but unexecuted; the prior queued candidate is unchanged.

## A-01: shape

The Swift actor becomes lock-confined state (`SyncCoordinatorState`). Every
check-and-set happens in one `synchronized` block that never suspends, so the claim
checks (`isSyncInProgress`, the advert/manual flags, waiter registration) are as atomic
as the actor's synchronous segments. `@MainActor` state (`state`, versions,
`lastSyncDate`) is backed by `StateFlow`s. Background work (suppression watchdog,
discovery monitoring, both retry loops) runs in an injected `CoroutineScope`; every
`Date()`, `ContinuousClock` and `Task.sleep` goes through an injected `SyncClock`.

The Swift extensions on `ConnectionManager` (`ConnectionManager+SyncRetry.swift`, plus
`detectAndStorePlatform` and `shouldPauseWiFiHeartbeatProbe`) become
`SyncRetryController`, driven through the `SyncRetryHost` port. `core:services`
cannot depend on `core:runtime`; the host members mirror the runtime
`ConnectionManager` getters of the same names (`connectionState`,
`detectedPlatform`, `lastCleanChannelSync`, `lastAttemptedChannelSync`).

## A-03: cancellation

Kotlin cancellation is prompt at every suspension point. Swift is cooperative, and
several Swift catch-alls absorb `CancellationError`. Kotlin never swallows the
*caller's* cancellation. It runs the same cleanup in `NonCancellable`, then rethrows:

- `runFullSync`: end the activity bracket once, then reset to idle (as Swift).
- `performResync`: drain handlers and resume notifications and auto-fetch, then rethrow.
  Swift returns `false`. Its success-path drain and resume are non-cancellable too.
- `onConnectionEstablished`: drain, resume and release the advert deferral, then rethrow.
- `retryChannels`: a cancelled advert wait rethrows. Swift returns a
  "Retry cancelled" result. Any cancellation after the claim (including one inside an
  activity callback) closes the bracket once and sets idle, then rethrows.
- `performAdvertContactSync`: cancellation rethrows. Swift returns `.failed`. WP-209's
  round already treats a cancelled handler as a cancelled round.
- `SyncRetryController.performInitialSync`: rethrows. Swift starts the resync loop.
- `onDisconnected` runs entirely in `NonCancellable`, because it is the safety net for
  stuck suppression and pills.

A `CancellationException` that a collaborator raises while the caller is still active
(an internal `withTimeout`, a foreign job) is an ordinary failure. Swift only
special-cases its own `CancellationError`, so a contact-stream timeout still gives
`.failed` and starts the resync loop.

In the resync loop, the bracket open, the success close plus promotion, and the
exhaustion branch (`onResyncFailed`, then the disconnect that cancels this same loop)
run in `NonCancellable`. The remaining success hooks (time sync, room re-auth,
`onDeviceSynced`) stay cancellable, with the cancellation and graph fence checked
between them where Swift checks. Both loop bodies catch and log any non-cancellation
throw instead of failing the scope. The injected scope should still carry a
`SupervisorJob`.

## A-04: collaborator failures

Swift declares most collaborator members non-throwing. Their Kotlin ports can throw.
Each such call (notifications, reaction index/queue/persist, heard-repeat
recording/harvest, RX-log cache updates, advert hooks, admin routing, activity and
phase callbacks, auto-fetch control) is wrapped. A throw is logged and the next step
runs, as if the Swift call had returned. Message handlers, the discovery monitor and
both retry loops can't be ended by a collaborator throw, and nothing reaches the
uncaught-exception handler. A `CancellationException` that a collaborator raises
while the caller is still active (an internal timeout) is logged as a failure.
Throwing members keep Swift's own `do/catch` and `try?` placement.

## A-05: claim ownership

Swift's `defer { isSyncInProgress = false }` can clear a newer claim. `onDisconnected`
clears the flag, a reconnect sync claims it, and then the old sync's `defer` clears
the reconnect's claim. The flag now carries a generation that every claim and
every disconnect bumps. A release only clears the claim it still owns. The advert
release still always wakes waiters. Native case:
`WP-214::a claim released after a disconnect cannot clear a newer sync's claim`.

Similarly, a resync or channel-retry job clears its stored slot only if it still
owns it. Swift checks `!Task.isCancelled` for the same purpose. The resync attempt
count is per loop.

`claimManualContactSync` re-checks the advert claim in the same critical section that
sets the manual flag, which closes the gap between Swift's two actor segments.

## A-06: Swift text semantics

- Blocked-sender lookup and the "message from my own node" self-mention check use
  canonical equivalence (NFC keys), matching Swift `String ==`/`Set<String>`.
- `parseChannelMessage` splits on `:` `Character`s (`\X` grapheme clusters). A colon
  that carries a combining mark isn't a separator. Only appended pieces count toward
  `maxSplits` (`"::a:b"` gives `a`/`b`). Trimming uses Foundation's
  `CharacterSet.whitespaces` exactly: tab, space, NBSP, U+1680, U+2000-U+200B, U+202F,
  U+205F and U+3000. That set includes U+200B and excludes U+180E. All of these values
  were captured from `swiftc` and are in `evidence/WP-214/swift-oracle/`.
- No regex shorthand classes are used. `\X` is supported by both the JVM and ICU, and
  merged `core:protocol` already uses it.

## A-07: numeric and Foundation edges

- `UInt32(date.timeIntervalSince1970)` traps outside `0...UInt32.max` in Swift. Kotlin
  clamps to that range. Affected: timestamp correction, sender stamps, the watermark
  reference.
- The reaction window `anchor + 300` saturates at `UInt32.max` instead of trapping.
- `Dictionary(uniqueKeysWithValues:)` traps on a duplicate channel slot. Kotlin keeps
  the last row.
- `error.localizedDescription` becomes the throwable's message (or its class name).
  `SyncCoordinatorError` messages are the Swift `LocalizedError` strings.

## A-08: identity and lifetime

- Swift `fetchContact(id:)`, `fetchRemoteNodeSession(id:)`, unread updates and similar
  calls are keyed by `EntityKey(radioId, id)` in the Android store. Sync passes the
  connection's radio. Room notifications look up the session on the handler's radio.
- Swift closures capture the coordinator `[weak self]`. Kotlin captures it strongly,
  so teardown must clear the polling handlers and the advert delta handler, cancel
  discovery monitoring, and finish data events (see the wiring section).
- `SyncDataEventBroadcaster` registers at `subscribe()` and unregisters when collection
  ends or `finish()` runs. Swift unregisters on deallocation. **A caller that subscribes
  must collect, and must collect each returned flow once.** A flow that is never
  collected stays registered and buffers until `finishDataEvents()`.
- `setState` writes the state flow and invokes `onPhaseChanged` without Swift's
  `@MainActor` hop. Concurrent writers (only possible across overlapping sync paths)
  may see callbacks out of order. The UI callback should read `stateFlow` rather than
  rely on callback order.
- `claimManualContactSync` keeps one deadline across re-waits, so repeated advert
  re-claims cannot stretch the 200 s bound.

## A-09: test adaptations

- Virtual time: a single-thread FIFO dispatcher plus a virtual `SyncClock`. Time only
  moves when nothing is runnable, earliest deadline first. Every Swift real-time
  wait (`waitUntil`, `Task.sleep`, the 2 s resync interval, the 200 s advert bound)
  runs deterministically.
- The SwiftData test store is an in-memory `PersistenceStoreProtocol` fake. Unmodeled
  members fail loudly. `ServiceContainer.forTesting` is replaced by recording fakes of
  each port.
- 11 ids exercise the real Swift `ContactService` (the 6 "Full sync prune ..." ids, the
  two epoch-zero advert prune checks, and three capacity connects). They run against
  `ReferenceContactService`, a test-local reference of `syncContacts`/`pruneOrphans`,
  through the `pruneContactServiceFactory` seam. WP-303 must point that seam at
  WP-209's `ContactService`.
- Four handler ids use real `HeardRepeatsService`/RX-log decryption in Swift. They run
  against fakes with the same observable contract. Undecryptable rows have no decoded
  text, and correlation requires a decrypted group-text row that rebuilds the key.
- `ConnectionManager` is `FakeSyncRetryHost`. Its `disconnect` models the effects the
  loops observe: cancel both loops, drop the graph, publish `.disconnected`.
- Smoke ids carry concrete checks. "wireMessageHandlers completes" asserts all four
  handlers are captured. "startDiscoveryEventMonitoring completes" asserts the
  monitor's start and cancel. "Post-sync diagnostics still run" asserts the store read
  and the RX-log refresh.

## Wiring WP-303 must do

1. Build `SyncDependencies` per connection from the real graph. Use WP-209
   `ContactService`/`ChannelService`, WP-208 `MessagePollingService`, the adapters in
   A-02, `startEventMonitoring` (weak container capture, as Swift) and
   `exportPrivateKey` from the session.
2. Implement `SyncRetryHost` over the runtime `ConnectionManager`. The runtime needs a
   new generation-checked entry point for `promoteToReadyAfterResync` (its promotion is
   private, and after a failed initial sync it stays `SYNCING`). Also needed: time
   sync, `onDeviceSynced`, the `awaitingReauth` map, `RESYNC_FAILED` disconnect and the
   `onResyncFailed` UI hook. `currentServices` must return the live generation's
   `SyncRetryServices` (identity per generation).
3. Call `RuntimeServices.initialSync` through `SyncRetryController.performInitialSync`.
   Feed `RuntimeServiceCallbacks.cleanChannelSync`/`channelSyncAttempted` from
   `setCleanChannelSyncCallback`/`setChannelSyncAttemptedCallback`.
4. Make the runtime WiFi heartbeat consult `shouldPauseWiFiHeartbeatProbe`. The runtime
   currently pauses only when not `READY`, not while a resync or channel-only retry is
   pending. Keep `storeDetectedPlatform` consistent with the runtime's identical
   WiFi→ESP32 resolution.
5. On disconnect: `cancelResyncLoop`, `cancelChannelRetry` and
   `onDisconnected(notificationService)`. On teardown: `cancelDiscoveryEventMonitoring`,
   `finishDataEvents`, `setDeltaSyncHandler(null)` and
   `messagePollingService.clearMessageHandlers()`.
6. Wire `setSyncActivityCallbacks` to the connection UI. Data-event consumers (app
   state, message dispatcher) must collect what they subscribe.
7. Rebind `pruneContactServiceFactory` to WP-209's `ContactService`.
8. Give the coordinator and controller a scope with a `SupervisorJob`.

## Channel-sync repair batch: active-link policy and typed channel failure

This bounded repair retains the source pin above and the original thirteen
`DevicePlatformChannelSyncConfigTests` families. It does not revise the source
platform matrix, ESP32's 30-second skip window, nRF52/unknown's zero window,
WiFi unknown-model fallback, or the runtime's READY-only heartbeat eligibility.
The App graph regressions supplement, rather than replace, those policy cases.
They observe the real channel session's pipeline capability query and emitted
channel requests over the Room-backed production graph, including replacement
graphs across BLE/WiFi reconnects.
Two additional native cases exercise 24 platform/transport/timestamp combinations
through the coordinator: clean and attempted timestamps at 29.999 and 30 seconds
must skip only on ESP32 before the boundary, never on nRF52 or unknown.

The original `Channel phase failure is partial and keeps connection usable`
case now injects `ChannelServiceError.CircuitBreakerOpen(3)` through the existing
`ChannelServiceProtocol.syncChannels` test seam instead of matching exception
text. Partial channels still permit a usable/Synced connection and exactly one
message poll. Caller cancellation remains a separate outcome: the existing
channel-phase cancellation case also requires zero message polls.
No new circuit-breaker producer or channel-failure recovery policy is introduced.
