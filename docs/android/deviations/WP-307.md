## Source-audit repair: live incoming channel avatars (#314)

This bounded repair starts from `fb9639bfd28ee77443b2a79b316d673ac21a5e1c` and preserves
the reference pin below. The existing rendering identity type was not connected to live
App conversations; type-level tests did not establish the missing consumer.

- **Native table boundary.** The App adapter builds the source's unique-name identity table
  and eligible local-photo map from the same contact snapshot, off the UI thread. Compose
  publishes them atomically and cancels obsolete calculations on contact/radio-route changes.
  The existing radio-scoped mention-contact stream supplies real contact updates, including
  image-byte changes with an unchanged `lastModified`. No second contact store or connection
  owner is created.
- **Native row boundary.** The real timeline reserves 28 dp plus a 6 dp gap for incoming
  channel rows, renders the avatar at the source's incoming-avatar cluster end, and reserves the same leading space for
  other rows in the cluster. Both App composition and the public timeline route preserve
  direct/outgoing exclusion. The native shared avatar's existing font-scale behavior also
  scales the reserved diameter at 200% font. Message/radio keys, chronological state,
  paging, unread/scroll anchors, retry, original text and rich-body actions are unchanged.
  Avatar clustering is separate from general row/day grouping: nil names break, empty
  names continue, canonical name equality is case-sensitive, and gaps through 300 seconds
  continue even across midnight. Day dividers retain their existing independent behavior.
- **Identity and media.** Name uniqueness does not require a nickname; collisions omit both
  the asserted contact identity and its photo. Avatar names use the contact's original name,
  not its nickname. The existing `IncomingAvatarIdentity.resolve` controls trimmed/canonical
  matching and initials-only prefix fallbacks. The existing byte-sensitive revision and
  bounded `AvatarImageCache` control replacement and native decoding; empty image bytes are
  absent rather than decoded. Decode failures retain the existing reported-failure behavior.
  Photo decoding is cancellable at the coroutine boundary, off the UI thread; the screen's
  bounded cache is cleared on disposal. Avatar chrome is hidden from accessibility, not a
  second sender announcement or interactive target.
- **Shared name-key policy.** Nickname and avatar tables share the source's scalar lowercase
  plus canonical-equivalence keys. The existing rendering-module text helper is internal,
  so this App-owned adapter keeps that small policy locally rather than widening a core API,
  adding a dependency, or applying JVM contextual final sigma. Original message/display text
  is never normalized or rewritten.
- **Acceptance boundary.** The 12 frozen configuration cases, three supplemental table/route
  cases and nine mounted App regressions are declared for Robolectric API 31/37. Their actual
  discovery and results require this candidate's own terminal hosted log. No local Kotlin,
  device, hardware, TalkBack, golden or incoming-flight-animation acceptance is claimed.
  The full WP-307 and WP-501 acceptance items remain unfinished.

The case mapping and actual local readiness outcome are in
`docs/android/evidence/WP-307/incoming-avatar-pipeline.md`. Hosted results remain in the

## Native adaptations

- **D-1 Reverse presentation, chronological state.** `ChatTimelineState.messages` and its row model stay
  oldest-to-newest. The Compose surface supplies `rows.asReversed()` to `LazyColumn(reverseLayout = true)`.
  Paging offsets, unread anchors, grouping, event admission, and persisted scroll anchors therefore do not
  inherit reversed indexes.
- **D-2 Feature dependency seam.** `ChatTimelineDependencies` is the feature-owned adapter boundary for
  persistence, retry, drafts, and the process/radio-owned event stream. The screen starts only its collector;
  it never constructs or cancels the radio session. `ChatTimelineRoute` can fill WP-306's existing detail
  pane without adding a feature-to-feature dependency.
- **D-3 Shared rendering boundary.** WP-307 renders safe plain message text, grouping, sender, day/unread
  dividers, and delivery/retry state. Link/inline-image/mention/emoji composition remains WP-308, and
  reactions/details/path/map actions remain WP-309. No second preview, rich-text, send, or WebView pipeline
  is introduced.
- **D-4 Screen restoration.** Drafts persist through the injected conversation-keyed store on every edit.
  Scroll restoration uses stable radio/message identity plus pixel offset. Re-entering a route may refresh
  the database window but cannot submit a message; accepted-send draft clearing remains an explicit call
  from the WP-308 composer.
- **D-5 Initial unread window.** The first fetch expands from 50 rows to unread count plus 12 rows of read
  context, capped at 200. A one-row lookahead proves whether older history exists. The persisted unread
  anchor is used when present; if it falls outside the bounded window, the oldest loaded row is the honest
  fallback rather than withholding the screen indefinitely.
- **D-6 UI verification.** The existing chats module has JVM state tests but no locked Compose UI-test
  dependencies. The Compose route/content compile and pass Android lint; deterministic JVM tests cover the
  reverse-order projection, stable keys, grouping, paging, anchors, event guards, delayed ACKs, retry,
  draft, reconnect refresh, and error-state transitions. Hardware scrolling, TalkBack, IME, and screenshot
  evidence are not claimed.

## Direct-message deletion recency (issue #202)

Frozen `ChatViewModel+MessageActions.swift` deletes a message and then recomputes
the direct contact's last-message date from the database before notifying the
conversation list. The mounted App adapter previously deleted and refreshed
without recomputation, leaving the deleted newest date or an empty conversation.
The existing store implementation is correct; an explicit store-only test cannot
prove that the App consumer calls it.

The adapter now awaits the existing recomputation for a direct message's
radio-partitioned contact key before refreshing conversations. It never derives
recency from the paginated timeline, changes channel or contactless recency, or
looks up the currently connected radio instead of the message's captured radio.
Room messages retain their separate adapter. Typed persistence failures and
caller cancellation propagate to the existing mounted action error handling.
Deletion and recomputation remain separate writes, as in the frozen consumer;
a failed recomputation does not imply that deletion rolled back.

the default page, deleting the last message, deleting older history, identical
IDs across radio partitions, channel/contactless exclusions, and a real
SQL-trigger recency failure after committed deletion. These add no original-case
credit or tapped-menu, UI paging, concurrency, API37, device or hardware proof.

whenever a newly loaded timeline appeared. During Activity recreation the old

precedence. This retains chronological data and reverse-layout projection and
does not initiate radio work or message sends.
