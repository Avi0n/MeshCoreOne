## Values and names

All 27 explicit wire IDs, widths, names, source units and declaration order are
preserved. Kotlin's enum `name` is reserved for its identifier, so the Swift
human-readable `name` becomes `displayName`; `fromName` remains exact and
case-sensitive. No localized names, extra units or RF formulas are introduced.
Integer values use `Long` for the source's 64-bit `Int`, including positive
`0x80000000..0xffffffff`. Unix dates use immutable `java.time.Instant` in seconds,
not a mutable JVM date or a platform API. Floating associated values override JVM
data-class equality/hashing so positive and negative zero remain equal as in
Swift; NaN still does not compare equal.

## Checked, atomic encoding

The original init/count/reset/encode and all 14 add methods are implemented.
`Bytes`, `ByteReader` and `ByteWriter` are the real merged WP-101 implementations;
big-endian LPP field helpers stay inside the owned LPP package.
All actual LPP fields in this source are big-endian. No little-endian field or
version-dependent extension is invented.

Swift numeric conversions/preconditions trap on invalid input. Kotlin rejects
nonfinite numbers, out-of-range quantized values, wrong associated value classes
and wrong raw widths with metadata-bearing `LPPEncodingException` subclasses,
before appending anything. Valid numeric conversion preserves IEEE multiplication
and truncation toward zero, not decimal rounding or saturation. For example,
`838.8607 * 10000` is `8388606.999999999` and encodes as `0x7ffffe`.

The source GPS helper converts to `Int32` and appends only its low 24 bits, so a
value outside the signed 24-bit field can wrap. As explicitly requested for this
WP, the native encoder instead rejects 24-bit overflow atomically. It does **not**
add geographic clamping/validation absent from the source: physical endpoints
are covered, and representable out-of-geographic-range wire coordinates remain
readable/encodable. Load and GPS sign extension use the full signed 24-bit range.
Humidity retains the source byte range (up to 127.5%), not a new 100% clamp.

`add(LPPDataPoint)` and `add(channel, type, value)` additionally encode all 27
source decoder value shapes, including colour, switch, signed load/current,
unsigned four-byte quantities and Unix time. These are native convenience
methods derived from the pinned decoder, not guessed firmware types.
Unix-time typed encoding rejects fractional seconds instead of silently losing
them. Raw encoding retains any correctly sized bytes, as in Swift.

The original `addCurrent(channel, milliamps: UShort)` preserves its unusual
unsigned input contract even though Swift decodes the field as signed: 32768
milliamps decodes to -32.768 A and 65535 to -0.001 A. Typed current encoding uses
the decoder's signed ampere value. This asymmetry is not silently corrected.
Every source four-byte scalar is **unsigned**; no signed-32 sensor is invented.

## Explicit partial decoding

Swift stops at the first unknown type, short header or short value and returns
the complete prefix, including an empty prefix on malformed input. Kotlin
preserves the same stop point, order, duplicate channels and prefix values,
but `decode` returns `LPPDecodeResult.Complete` or `Incomplete`, never a
success-shaped empty list for an invalid frame. `Incomplete` exposes a typed
diagnostic at the failing record's starting offset, the accepted byte count and
the entire unconsumed record/suffix. It does not skip unknown data or resynchronize.
`decodeStrict`/`requireComplete` throw `LPPDecodingException` carrying that same
diagnostic. A genuinely empty payload is still complete.

Decoded collections are defensively copied and unmodifiable. A later telemetry
consumer in WP-106 can deliberately expose `dataPoints` while also retaining the
incomplete diagnostic; this WP does not edit or stub the unported event consumer.
No bounds exception is caught and converted to zero. All widths are checked
before the checked reader consumes a value.

## Evidence and scope boundary

### R118 malformed-suffix and encoder reconciliation (#377)

The stricter API above remains an intentional native adaptation, not identical
Swift failure behavior. A Swift caller gets only the accepted prefix; a Kotlin
caller gets that same prefix plus an explicit completion state and lossless
suffix. The actual `TelemetryResponse.dataPoints` consumer exposes the prefix
without calling `requireComplete`, and its `decodeResult` retains the diagnostic.
Only callers choosing `decodeStrict`/`requireComplete` reject the whole result.
Returning `Complete` for malformed tails or throwing away the accepted prefix
would violate this contract.

Swift conversion traps do not provide recoverable errors or an atomicity promise;
GPS additionally accepts an Int32 then discards its high byte. Kotlin deliberately
keeps checked, atomic failures, including rejection of signed-24-bit GPS overflow.
No new geographic restriction is added. Rejection metadata and subsequent valid
appends are tested through the original floating encoder entry points, not only
the native typed `add` convenience method. This repair changes no production
behavior and does not infer human approval of the adaptation from passing tests.

The [R118 reconciliation](../evidence/WP-105/r118-contract-reconciliation.md)
accounts for all 23 assigned original families, independent complete results,
three malformed-tail shapes per family, the real telemetry consumer, and
recoverable encoder failures. The historical evidence below remains attributed
to its original candidate.

The [WP evidence](../evidence/WP-105/README.md) records the original-case mapping,
independent fixtures, concrete commands and discovered outcomes. Assertions
cover every type independently in both directions, malformed suffixes, all raw
boolean bytes, signed/unsigned extrema, GPS limits, nonfinite input, atomic
failures, immutable snapshots and supplementary seeded properties.
